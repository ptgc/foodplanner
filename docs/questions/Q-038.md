# Q-038: Household plan storage: separate tenant table or columns on Household
Raised by: spec writer, task T-123
Status: answered

## Context
T-123 gives each household a plan (Claude limits per household: photo imports per day, line help per day and per month, each a number or unlimited, plus an optional label). The limiter (T-077, T-118) reads it on every reservation, the super admin writes it inside a write support session (T-096), and the local seed must make the architect's "Home" household unlimited without a real admin action. Neither ADR 0001-0009 nor `docs/domain.md` says where per-household settings of this kind live. Rule 1 says every household-owned entity is an `ITenantEntity`; `Household` itself is the tenant root and is exempt (it has the name and nothing else).

The two shapes differ in how the tenancy guarantees work and in how the seed writes.

## Options
1. **A new table `HouseholdPlans`, a tenant entity (`ITenantEntity`, unique index on `HouseholdId`).** A row means "this household has a custom plan"; no row means "use the configured defaults". Each limit is a nullable int (`null` = unlimited). The read goes through the tenant filter, and the support write goes through the write guard, so a plan can only be read or written for the session's household by construction. It joins the tenant-isolation suite and household deletion (T-044) like any entity. Cost: the seed has to write a tenant entity outside a request, which needs one new named member on `ITenantResolution` (the only place allowed to open the write scope; Q-006), used by the seeder only; and one extra query per reservation.
2. **Columns on `Household`** (`PlanName`, `PhotoImportsPerDay`, `LineHelpPerDay`, `LineHelpPerMonth`, plus a flag that says "custom plan", because `null` would otherwise mean both "default" and "unlimited"). No new table, no extra query (the household row is cheap to read), and the seeder simply sets the columns where it already creates the household. Cost: `Household` is not a tenant entity, so no filter or write guard protects these columns; correctness rests on the handler using `ICurrentHousehold.HouseholdId` and never a route value (the same discipline the overview already relies on). The root grows into a settings bag as more plan fields arrive.
3. **Columns on `Household` as one JSON column** (`PlanJson`, null = defaults). Easiest to extend with new limits (own key, Oda) without a migration each time; but limits are not queryable or checkable by the database, and the shape needs its own versioning.

## Recommendation
Option 1. It is the only shape that keeps rule 1 literal (household-owned data is a tenant entity and the guard enforces "only this household"), it makes "no row = defaults, delete the row = reset" natural, and the support write needs no special case. The cost (one resolution method for the seed, one query) is small and contained. The spec assumes option 1; if the answer is 2 or 3, only the Data model, Migration, Seeding and the isolation-suite criteria change.

## Answer (architect)

Answered 2026-11-22 by the architect: option 1 (a separate tenant table HouseholdPlans), as recommended.

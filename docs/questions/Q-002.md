# Q-002: Email confirmation for local accounts in M0
Raised by: spec-writer / task T-009 (also affects T-010)
Status: answered

## Context
T-009 adds local registration and login. ADR 0004 says accounts link "only by verified email", and T-010 auto-links a Google login to an existing user with the same email. If a local account can be created without proving the email, an attacker can register `victim@example.com` with a password first and then share the account once the real owner signs in with Google (pre-account hijacking). Registration that answers "email already taken" also lets anyone find out who has an account (user enumeration).

Email confirmation needs a way to send email. `/src/Infrastructure` lists "email", but no backlog task delivers an email sender or provider. Neither ADR 0004 nor the T-009 task decides whether local accounts must be confirmed.

## Options
1. **Confirm email in T-009.** Add an `IEmailSender` abstraction with a dev/test implementation that records messages (tests read the link from it). Register always returns 202 with the same body. A new address gets a confirmation mail; an existing one gets a "you already have an account" mail. Login is refused (with the generic login failure) until the email is confirmed. T-010 links only to confirmed users. Trade-off: T-009 grows a bit, and a real email provider (new backlog task, plus Key Vault secret) is needed before real users can register locally.
2. **No confirmation in M0.** Local accounts are usable immediately. Duplicate registration returns 409, which accepts enumeration on register. T-010 never links to an unconfirmed local account. Instead, a verified external login for that email takes the account over: the password is removed and the email is marked confirmed. Trade-off: no email dependency now, but enumeration is possible and the takeover rule is subtle security code.
3. **No local self-registration in M0.** Sign-up is Google-only (T-010). The local login code exists but accounts are only created by tests or dev seeding, until an email task lands. Trade-off: smallest attack surface, but it departs from the "local fallback" in ADR 0004 for now, and families without Google cannot join.

## Recommendation
Option 1. It is the only option that meets both "link only by verified email" and "no user enumeration" without special-case takeover logic. The dev/test sender keeps M0 independent of a real provider. Add a backlog task for the production email sender.

## Answer (architect)
Decided 2026-10-22: option 1. T-009 adds email confirmation with an IEmailSender port and a recording dev/test sender. Register always returns 202 with the same body. Login is refused until the email is confirmed. T-010 links only to confirmed users. The production email provider is task T-017 (provider choice: Q-007).

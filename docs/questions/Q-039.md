# Q-039: Run size and time limits for "Sync with Oda" (T-130)
Raised by: spec-writer / task T-130
Status: open

## Context
"Sync with Oda" searches Oda for every ingredient used in the household's recipes in one session-only connection (T-130 spec, ADR 0008 decision 2026-11-20, Q-024/Q-025). `product_search` takes at most 10 queries per call, so 150 ingredients cost 15 searches plus one `likely_to_buy`. Neither ADR 0008 nor the T-053 spec says how many calls one connection may make: Oda's usage limits are not published (T-053 only says a 429 ends the action and is never worked around), and the access token lifetime has not been observed (T-053 implementation check 4). A large household could have 300+ ingredients. The spec needs a cap, a time limit and a rule for what happens above them. These are numbers and behaviour the product owner should accept, not something the spec writer should decide.

## Options
1. Cap per run plus continuation. One run checks at most `Oda:MaxSyncIngredients` (default 200, so at most 20 searches + 1 history call), ordered by how many recipes use the ingredient (most used first), then name. A time budget `Oda:SyncBudgetSeconds` (default 90) is checked before every call; when it is spent, or Oda answers 429 or an error after the first batch, the run stops and returns what it has plus how many ingredients were not checked. The review screen offers "Check the next ones" which starts a new sign-in with an offset. Trade-off: a second sign-in for big households, but each connection stays short and the call count is predictable.
2. No cap, only the time budget and 429 handling. One run goes through all ingredients until the budget (90 s) or Oda stops it; the rest is reported as not checked and the user simply runs again (ingredients that got a choice are skipped next time, so the run moves on; "not found" ingredients are searched again). Trade-off: simplest, but a large household may need several runs with no predictable end, and not-found rows can crowd out the unchecked ones.
3. Hard refusal above a cap (for example 150): "too many ingredients, remove or hide some", as `Oda:MaxItemsPerAction` does for the cart. Trade-off: very predictable and simplest to test, but a household with many recipes cannot use the feature at all.

## Recommendation
Option 1 with the defaults above (200 per run, 90 s budget, searches strictly sequential, a 429 or other Oda error after the first batch ends the run with partial results, never retried). It keeps each connection short, respects the usage limits conservatively, and gives a large household a way through. Record the observed Oda call counts and token lifetime in the PR notes of T-130 and tune the numbers afterwards.

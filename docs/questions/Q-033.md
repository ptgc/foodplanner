# Q-033: Where does the Oda sign-in flow state live across API replicas (T-053)
Raised by: spec-writer / task T-053
Status: answered (2026-11-20)

## Context
The session-only Oda flow (Q-024/Q-025 answers, 2026-11-20) is an OAuth authorization code flow with PKCE S256. It has two HTTP calls that can be served by different replicas of the API on Azure Container Apps: the call that starts the flow (creates the PKCE `code_verifier` and `state`, returns the Oda authorize URL) and the call that completes it (receives the `code` after the redirect back to Foodplanner's own origin, must present the same `code_verifier` and check the same `state`). With more than one replica, in-memory state of the first call is not on the second replica.

The Oda access token is different. The T-053 spec lets the complete call do everything in ONE request on one replica: exchange the code, search, fill the cart, revoke, respond. So the token is only ever in that request's memory and nothing has to carry it. The open point is only the short-lived flow state (verifier, state, which household and week, which user, expiry). The verifier is not an Oda credential on its own (it is useless without the code, and the code is single use) but it should not be logged and should be short-lived.

ADR 0005/0007 do not say how replicas share short-lived state. T-009 notes that persisting the ASP.NET Data Protection key ring for deployed environments is not assigned, which options 1 depends on.

## Options
1. Stateless: the start call returns the flow state in a short-lived, encrypted, `HttpOnly`, `Secure`, `SameSite=Lax`, `__Host-` cookie (ASP.NET Data Protection, 10 minutes, contains verifier, state, household id, week, user id). The complete call reads and deletes it. Any replica can serve both calls if they share the Data Protection key ring (a key ring in Blob or Key Vault, not currently assigned to a task; T-009 says deployed environments have no persistent key ring yet, and the same ring would also be needed by the auth cookie once there is more than one replica). No new table, no migration. State lives in the browser that started the flow, which is the browser that comes back.
2. Session affinity on Container Apps (sticky sessions) plus in-memory state with a 10 minute expiry. No key ring or table. Fails when the replica restarts or scales in between the two calls, and affinity is an infrastructure setting that must be set in Bicep and then stays a hidden requirement of the feature. The user sees "sign-in expired, try again" in those cases.
3. A short-lived row in SQL (`OdaFlowState`: state hash, verifier, household, user, expires, single use) or a shared distributed cache. Works for any replica without cookies or key ring. Adds an entity (tenant-scoped, isolation suite, migration `Migration: yes`, cleanup job) and writes the verifier to the database for a few minutes.

## Recommendation
Option 1, and state that the Data Protection key ring must be shared and persisted for any deployment with more than one replica (a separate infra task, needed anyway for the auth cookie). Until then a single replica works for local and the first environments. It keeps "nothing stored" literally true (no row, only a short-lived cookie) and keeps T-053 at `Migration: no`. Option 3 is the fallback if the architect prefers server-side state to a key-ring dependency.

## Answer (architect)
2026-11-20: Option 1. The flow state (verifier, state, household, week, user) travels in a short-lived (10 minutes) encrypted `__Host-` cookie in the browser that started the flow. There is no table and no migration, so T-053 stays `Migration: no`.

The Data Protection key ring must be shared and persisted before any deployment runs more than one API replica. The auth cookie needs the same. That is a separate infra task that doesn't exist yet. Until then a single replica works.

# Q-025: Where and how do we keep a household member's Oda tokens beyond the spike?
Raised by: implementer-backend / task T-001
Status: open

## Context
Oda MCP uses OAuth 2.1 style sign-in (authorization code + PKCE S256, dynamic client registration, scope `mcp`, token endpoint auth `none` or client secret; metadata in `spikes/oda/findings/as-metadata.json`). There is no API key and no password for us to hold, only an access token and a refresh token issued per registered client. The spike keeps them in .NET user secrets (rule 7, never in the repo). Foodplanner at runtime would hold them for real households. T-099 (encrypted external credentials, Depends on T-001) plans application-level encryption per household with keys outside the database, but it does not yet say:
- whose token it is (the member who signed in, tied to `UserId` + `HouseholdId`, or a household-wide credential);
- what happens when that member leaves the household, is removed, or revokes access in Oda (Privacy & security);
- whether we register one client per household (DCR) or one shared client for the whole app (a redirect URI on our own domain instead of loopback);
- how the refresh token lifetime and rotation (not measured in Phase B: refresh was implemented but never exercised, so lifetime and rotation are still unknown) is handled when a household is idle for weeks.
ADR 0004 (auth) and 0005 (tenancy) do not cover third-party tokens.

## Options
1. Token per member (`ExternalConnection` entity: UserId, HouseholdId, provider, encrypted refresh token, expiry); deleted when the member leaves. Clear ownership, matches the ToS idea that the connected account is one person's. One shared app-wide DCR client with our own HTTPS redirect URI.
2. One token per household (the "Oda owner"), owner-only management, replaced on re-connect. Simpler UI, but breaks when that person leaves and blurs "on behalf of others" (see Q-024).
3. No server-side storage at all (assistant-bridge route, Q-024 option 3). Nothing to protect.

## Recommendation
Option 3 as default; if Q-024 allows a direct client, option 1 with T-099 encryption (ASP.NET Data Protection key ring or Key Vault key wrapping, keys in Key Vault via managed identity), only the refresh token stored, access tokens kept in memory, row tenant-scoped and added to the tenant-isolation suite. Phase B did not measure lifetime or rotation (refresh untested); measure them before deciding, e.g. in T-053 or T-099.

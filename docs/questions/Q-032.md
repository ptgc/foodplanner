# Q-032: May Foodplanner keep the household's chosen Oda product per ingredient (T-052, T-053)
Raised by: spec-writer / task T-053
Status: answered (2026-11-20)

## Context
Q-024 and Q-025 (answered 2026-11-20) decided that the Oda connection is session-only and that nothing from the connection is stored: no token, no refresh token. Q-024 option 2 said "store at most the Oda product id the user picked, per household", but the architect's answer did not take over that sentence, and the orchestrator note says search only for the items being added, with no product or price collection beyond that.

T-052 (`IngredientProductMapping`: household, ingredient to provider SKU, Migration: yes, T-053 depends on it) stores exactly such a mapping. Oda's terms (`spikes/oda/findings/tos-mcp-section.md`) forbid collecting products or prices beyond the user's own shopping. A stored Oda product id (integer, no name, no price) per ingredient is small and tied to the household's own choices, but it is still Oda product data kept after the session, and the id may go stale (Phase B: server changes, pack sizes differ). Phase B also showed that search alone mis-ranks some names ("karbonadedeig", "Nøytral olje") and returns several pack sizes, so without a stored preference the household cannot make Oda pick the same product every week; the user fixes it in the Oda cart each time.

ADR 0008 and the Q-024/Q-025 answers do not decide this. The T-053 spec leaves the mapping out (it works with search only) until this is answered.

## Options
1. Do not store any Oda product id. T-053 searches every time and takes the top available hit. T-052 is cancelled or reduced to nothing for Oda. Simplest and clearly inside "nothing is stored"; the household repairs mismatches in Oda every week.
2. Store only the Oda product id per (household, ingredient), set by an Adult who picks a product, and use it instead of searching for that ingredient. No name, price, brand or any search result is stored. Better repeat accuracy; stale ids must be handled (unavailable id falls back to search, and the mapping is dropped or flagged). A small stored Oda data set per household remains, which the terms may or may not allow.
3. As option 2, but only after Oda confirms in writing that keeping a product id per household is fine (Q-024 option 1 for this one point). Safest legally; T-052 and the mapping part of T-053 wait.

## Recommendation
Option 1 for T-053 now: it matches the architect's answer literally, needs no migration and no extra approval, and the fix-in-Oda step is already part of the decided flow. Keep option 3 as the path if the household finds the weekly fixes too tedious. Then T-052 needs a decision (cancel, or re-scope), which is for the architect.

## Answer (architect)
2026-11-20: Now option 1. T-053 stores no Oda product id: it searches every time and adds the first available hit, and the household swaps or fixes products in Oda afterwards. T-053 no longer depends on T-052.

Later, getting the right product from the start matters. Examples are a particular kind of cherry tomatoes, mayonnaise or cheese. Two later tasks cover it:
- **T-114, prefer what the household usually buys.** During the same session-only cart fill, read the household's own Oda purchase history (`likely_to_buy`, `get_orders`/`get_order`) and prefer a search hit the household has bought before. Nothing is stored.
- **T-052 (re-scoped), preferred product per ingredient.** An Adult picks "this one, not that one" per ingredient, and Foodplanner keeps only the Oda product id per household and ingredient (option 2). No written confirmation from Oda is required, in line with the Q-024 answer.

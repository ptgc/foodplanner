# Q-014: Image library for T-022 (ImageSharp needs a license key to build, older versions have known vulnerabilities)
Raised by: implementer-backend / T-022
Status: open

## Context
T-022 says "generate fixed sizes with ImageSharp" (ADR 0007 only says "resized to fixed sizes on upload"). Checked against nuget.org on 2026-10-24:

- **SixLabors.ImageSharp 3.1.12 and 3.2.0** (the last 3.x) carry known advisories (GHSA-gwg2-r3hj-4w44 moderate, GHSA-wmxv-xphr-5c9g moderate, GHSA-j3p4-wp97-rph4 high, GHSA-j9gm-c75j-xc9q high, GHSA-jjfr-hcj7-qf5w high). `dotnet build` fails on them (NU1902/NU1903, warnings are errors). Uploads are untrusted input, so suppressing them is not acceptable.
- **SixLabors.ImageSharp 4.1.3** (first version without open advisories) ships an MSBuild target (`SixLabors_ValidateLicense`, before CoreCompile) that **fails every non-Debug build** with "No Six Labors license found. Set $(SixLaborsLicenseKey), set $(SixLaborsLicenseFile), or add a 'sixlabors.lic' file". verify.sh builds Release, the Dockerfile builds Release, CI builds Release. Six Labors' pricing FAQ says a key is required to build and a purchased key comes by email after a 30-day trial key. Whether projects that qualify for the Apache-2.0 half of the Split License (open source, non-profit, or for-profit under 1M USD revenue) get a free key could not be confirmed from the public docs.
- Licence text (4.1.3): Apache-2.0 if the consuming software is open source, or the consumer is a for-profit under 1M USD annual gross revenue, or a non-profit; otherwise the paid Commercial License.

I cannot obtain or choose a key, and a key would have to be a secret in CI and in the Docker build (CLAUDE.md rule 7), on every contributor machine, and in Dependabot-style restores. That is a product/licensing/security decision, so I stopped the image-processing part.

## Options
1. **Stay on ImageSharp 4.1.x with a Six Labors license key.** Architect obtains the key (confirms whether the Apache half is free and gives a key). Wire it as `SixLaborsLicenseKey` (CI secret, Docker build secret, user secret or untracked `sixlabors.lic` locally). Matches the task text. Cost: key handling in every build, a build that fails without it.
2. **Use a permissive library without a build key, with native libs: NetVips (MIT, libvips; shrink-on-load, low memory, strips metadata, WebP/JPEG/PNG) or SkiaSharp (MIT; decode/resize/encode WebP).** Same design (sniff, limits, three WebP sizes, versioned blobs); only the processor class changes. Cost: native binaries in the container (NuGet runtime packages cover linux-x64 and win-x64), a task text change.
3. **Pin 3.1.12 and suppress NU1902/NU1903.** No key, matches the task text. Cost: shipping known high-severity decoder vulnerabilities on an upload endpoint. Not recommended.

## Recommendation
Option 2 (NetVips first, SkiaSharp as the alternative). It needs no secret in builds, so verify.sh, Docker, CI and new contributors keep working unchanged, and it avoids a licence relationship the architect has not chosen. If the architect prefers to hold a Six Labors licence anyway, option 1 is a contained change: the processor is already one class (`RecipeImageProcessor`) behind the endpoints.

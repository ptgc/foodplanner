# Q-012: Enforce same-household references in the database?
Raised by: orchestrator (from opus review of T-012) / affects T-021, T-030, T-033
Status: open

## Context
The tenancy filter and save guard (T-008) stop a household from reading or writing another household's rows. They do not stop a household from *referencing* another household's row by id: a RecipeIngredient (household A) can be saved with an IngredientId that belongs to household B, or a join row can link A's recipe to B's tag. T-012 added `CrossHouseholdLinks`, a test helper that finds such links, and documented the rule "resolve referenced ids through the filtered DbSet before saving" for T-021+. That is a convention plus a test check, not an enforced guarantee.

T-020 also adds global catalog rows (Ingredient/Unit with HouseholdId = null, ADR 0005), so a household-owned row may legitimately reference either its own household's row or a global row.

## Options
1. Convention only (current): handlers resolve every referenced id through the filtered DbSet (a foreign id resolves to null → 404/400), plus the T-012 test helper run over the whole test database after every test run.
2. Composite foreign keys: `(HouseholdId, ParentId) -> (HouseholdId, Id)` on an alternate key, so SQL Server rejects cross-household references. Clean for household-to-household references, but does not work for references to global rows (HouseholdId null), which need option 1 or a separate global table.
3. A save-interceptor check: before SaveChanges, for every modified foreign key on a tenant entity, verify the referenced row is in the same household or global. Enforced in one place, extra queries per save.

## Recommendation
Option 1 now (no schema impact, T-021 can start), and option 3 as a follow-up task once T-021 shows the reference patterns, because it also covers global rows. Option 2 only if option 3 proves too slow.

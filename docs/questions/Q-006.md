# Q-006: Tenancy of Membership, Invite and Household (lookups before a household context exists)
Raised by: spec-writer / task T-011 (also affects T-008, T-012)
Status: open

## Context
CLAUDE.md rule 1: every household-owned entity implements `ITenantEntity`, and the global filter (T-008) hides rows that are not in the current household. Some T-011 lookups must work before or across household contexts:
- resolving the caller's membership to build `ICurrentHousehold`
- `GET /api/households` (all households the user belongs to)
- accepting an invite by token, which the user is not yet a member of

If Membership and Invite are `ITenantEntity`, these queries must bypass the filter. If they are not, they escape the isolation suite (T-012). `Household` is the tenant root and has no `HouseholdId` of its own. ADR 0005 does not cover this.

## Options
1. **Tenant entities with one sanctioned bypass.** Membership and Invite implement `ITenantEntity`. A single Infrastructure service (for example `ITenantResolution` with `GetMembershipsForUser(userId)` and `FindInviteByTokenHash(hash)`) is the only code allowed to call `IgnoreQueryFilters`, always with an explicit `UserId` or token-hash predicate. An architecture test (T-012) fails on any other `IgnoreQueryFilters` call site. Household is exempt as the tenant root and listed in T-012's explicit exemption list. Trade-off: one controlled hole, and everything else stays filtered.
2. **Identity-level entities.** Membership, Invite and Household are not `ITenantEntity`. They go on an explicit exemption list in T-012, and every query on them filters by `UserId` or `HouseholdId` by hand, with dedicated authorization tests. Trade-off: no bypass mechanism, but manual filtering is the exact mistake the global filter exists to prevent. For example, a future "list members" query could leak.
3. **Separate unfiltered resolution context.** A small read-only `TenantResolutionDbContext` maps the same tables without filters and is used only by the membership resolver and invite redemption. `AppDbContext` owns migrations and keeps filters everywhere. Trade-off: clean separation, but two contexts map the same tables, and you have to make sure the second one never writes or drifts.

## Recommendation
Option 1. It keeps rule 1 literally true, so member lists and invites are isolated by default. The bypass is one auditable service guarded by an architecture test.

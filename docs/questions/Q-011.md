# Q-011: Re-registering an unconfirmed address, and squatter accounts
Raised by: orchestrator (from opus review of T-009) / task T-009, affects T-010
Status: answered

## Context
The T-009 spec says that registering an address that already exists sends a "you already have an account" email with no token. The first T-009 implementation re-sent a confirmation link for existing *unconfirmed* addresses, so a user stuck with an expired link could recover. The reviewer rejected that: an attacker who pre-registers `victim@x` with their own password could get the victim to confirm the attacker's account (pre-account hijack, the risk Q-002 was meant to prevent). T-009 now follows the spec literally.

Leftover effect: an unconfirmed account created by someone else (a squatter) is permanent. There is no resend, reset or expiry, and T-010 rule 4 sends a Google login for that email to `account-conflict` forever. The real owner can never register that email.

## Options
1. Keep the spec as is (current T-009). Accept squatter accounts until password reset exists.
2. Re-registering an unconfirmed address replaces the password hash with the new registrant's, rotates the security stamp (all earlier links die) and sends a fresh link. A link then always confirms the latest registrant's password. Small change in T-009's handler.
   Reviewer (opus, T-009 re-review): this does not hold if the attacker re-registers *after* the victim. The stamp rotates again and the victim's newest link confirms the attacker's password. Every link lands in the victim's inbox, so whoever registered last wins and the victim can't tell which registration a link belongs to.
3. Delete unconfirmed accounts after the confirmation window (e.g. 24 h) with a background job, so the address frees up.
4. Choose the password at confirm time: register only records the email and sends a link; the link opens a "set your password" step, and only then does the account get a password and become confirmed. An attacker never controls the password of an account the victim confirms.

## Recommendation
Option 4, plus option 3 to free squatted addresses. Option 4 changes the T-009 register/confirm contract and needs a small screen in T-028, so it belongs in a follow-up task, not the current T-009. Until then, option 1 (the current behaviour) is safe; only the stuck-user UX is missing.

## Answer (architect)
Option 4 (set the password at confirm time) plus option 3 (remove expired unconfirmed accounts), decided by the architect on 2026-10-24. Implemented by T-072.

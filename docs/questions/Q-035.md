# Q-035: Where does the cropped dish picture live between the photo import and "save"?
Raised by: spec-writer, task T-118 (docs/specs/T-118-recipe-from-photo.md)
Status: answered

## Context
A photo import produces an import draft that the household checks before saving (T-118, T-119). When the page has a photo of the dish, the server crops it (NetVips) and offers it as the recipe picture in the review. The picture must survive from the import request until the household presses save (minutes, or days if the draft is left waiting), and must be gone once the draft is saved or discarded. Today an import draft is only JSON on `RecipeImport` (no binary data) and `imageUrl` is a candidate URL that is never downloaded (docs/domain.md "Recipe import"). No ADR decides where a draft's binary lives. The uploaded photos themselves are never stored; this is only about the small crop (WebP, at most about 150 KB at the `card` size).

## Options
1. **A temporary blob in the existing image store (Azurite / Blob), name `{householdId:N}/imports/{importId:N}/picture.webp`, deleted on save (after the real recipe image is made from it), on discard, and by a sweep of drafts older than N days.** No migration for the bytes; reuses `IImageStore` and the household prefix delete (T-044). Cost: a second place that must be cleaned (orphans if a delete fails, as with recipe images today).
2. A `varbinary(max)` column on `RecipeImports` (one more migration). Deleted with the row's erasure on save and discard, so the draft's lifecycle and the picture's are one row and one transaction. Cost: binary in the main database, bigger backups; the 50-draft cap bounds it (about 7 MB at most).
3. Do not store the crop: keep only the normalized box and photo index in the draft, and ask the user to upload the photo again at save to crop it. Nothing extra stored, but the photo is not kept, so this does not work (the photo is deleted after the import by rule).

## Recommendation
Option 1. It follows how recipe images already work, needs no change to the import table, and the crop is small. Cleanup of orphans is already an accepted trade-off for recipe images; the spec adds deletion on save and discard and a "draft older than 14 days" sweep only if the existing hosted-service pattern makes it cheap (otherwise a follow-up). Option 2 is acceptable if the architect prefers one transactional lifecycle.

## Answer (architect)

Answered 2026-11-22 by the architect: go with the recommendation.

# Q-023: System admin for household support (T-096)
Raised by: spec writer / task T-096
Status: open

## Context
Architect request 2026-10-29: a system admin who can do support work on households without being a member of each. This is the most sensitive change in the app (CLAUDE.md rules 1 and 2, ADR 0005). The spec ([T-096](../specs/T-096-system-admin.md)) is written assuming the recommendation of every point below. Nothing in ADR 0004 or 0005 decides these. Common design, not a question: no global filter bypass; a support session scoped to one household, with a reason, sets the same tenant filter a member would have (role null), so every read and write stays inside that one household; every support request writes an append-only audit row.

## Options

### 1. How does someone become system admin, and how is it revoked?
1. Configuration allow-list (`Support:SystemAdminEmails`, Key Vault-backed in test/prod, `appsettings.Development.json` for the seeded local admin). Matched against the signed-in account's CONFIRMED email on every request. Revoke = remove from the list and redeploy/restart. Never stored in the database, so nothing in the app can grant it.
2. A flag on the user row (`IsSystemAdmin`), set only by a CLI/migration-bundle command run by the architect. Revoke = run the command. Survives config mistakes, but needs a migration and adds a column on the identity table that code could in theory write.
3. A separate admin identity (own login, e.g. Entra) apart from family accounts. Strongest separation, but a second auth stack that ADR 0004 declined.

### 2. How far can support go (read versus write)?
1. Read-only everywhere (look, never fix). Safest, but cannot fix a lost Owner, stuck invite, PIN lockout or locked week, which is the request.
2. Read-only views plus a small closed list of named fixes: cancel an open invite, promote an existing member to Owner, clear a PIN lockout, unlock a week. Writes need a separate write-mode session with password re-entry. No generic editing, no creating invites or adding people.
3. Read plus generic edit of any household data. Most flexible, but a general-purpose cross-tenant write path that cannot be reviewed action by action.

### 3. Does the household have to agree before support gets in?
1. No prior consent: admin starts a session with a mandatory reason, everything is audited and the household is told (point 4). Fast; works when the person asking is not the Owner or the Owner is gone.
2. Owner must switch on "allow support for 24 h" first. Strongest privacy, but fails exactly the lost-Owner case and adds a consent flow.
3. Consent for write mode only (read needs none). Compromise; still blocks the lost-Owner fix unless an Owner exists.

### 4. What does the household see?
1. In-app "Support access" log for Owners and Adults (when, read or write, reason CATEGORY, actions taken; admin shown as "Foodplanner support", free-text note hidden) plus an email to all Owners whenever a write session starts or a write action runs. Reads are only logged in-app.
2. In-app log only, no email.
3. Email to Owners for every session, read included, with the admin's name and the full reason text. Most transparent, but noisy and may expose personal detail typed in the note.

### 5. Audit log immutability and retention
1. Append-only table `SupportAuditEntries`: the app can only insert (save guard refuses update/delete) and a SQL trigger refuses UPDATE/DELETE from any login; no FK to households or users so deleting either keeps the rows; kept indefinitely; each row is also written to the structured log.
2. As 1, plus a copy in immutable (WORM) blob storage or a Log Analytics workspace with locked retention. Tamper-evident even against a database owner; extra Azure resources and cost.
3. Rows kept 24 months, then purged by a scheduled job. Smaller data, but the purge is a path that deletes audit rows, which conflicts with "never editable".

## Recommendation
1. Option 1 (config allow-list of confirmed emails). Cannot be self-assigned or granted from inside the app; revocation is immediate on the next request after the config change; no migration for the role itself.
2. Option 2. It covers the four support cases in the request and nothing more; each write is a named, tested action reusing the Owner-endpoint domain code. Generic edit can be added later by a new spec.
3. Option 1 for v1, because the lost-Owner case needs it. Compensate with point 4 and the audit log. Revisit option 3 if households ask for control.
4. Option 1. The household can always see that support was there and why in broad terms; the email goes only for changes, which are the events a household would worry about.
5. Option 1 now (trigger plus guard plus log mirror), keep forever (rows are small). Move to option 2 if the app ever has external customers or a compliance need.

# Q-020: Kid profile lock, PIN and who may manage profiles
Raised by: spec writer / T-026
Status: open

## Context
T-026 adds credential-less kid profiles that are picked on a device where an adult is signed in, and a PIN to get back to the adult. ADR 0004 (cookie auth) and `docs/domain.md` (roles per membership, "A Child profile can never perform Adult-only actions, regardless of device login") say what must hold but not how the lock and the PIN work. These are security and product choices, so the spec (`docs/specs/T-026-kid-profiles.md`) assumes the recommendations below and marks every part that depends on them with "(Q-020 n)".

## Options

### 1. Whose PIN, and what is it for
1. One PIN per account (user), set by the adult in their own settings; unlocking checks the PIN of the account that is signed in on the device. Stored in a global table next to the login.
2. One household PIN set by the Owner that every Adult shares. Simple to remember; any adult (and anyone who learns it) unlocks any adult's session, and it is per household while the session is not.
3. No PIN: return by re-entering the account password. No new secret, but external-login users (T-010) have no password and typing a password in front of kids is awkward.

### 2. PIN format and lockout
1. 4 to 8 digits, PBKDF2 hash with per-PIN salt. After 5 consecutive wrong PINs the account's PIN is locked for 15 minutes (server-side counter, so clearing cookies does not reset it), plus a per-IP-and-user rate limit of 10 attempts per minute. While locked, even the right PIN is refused; signing in again with the password is always the way out.
2. Same hash, but lockout doubles each time (1, 2, 4 ... up to 60 minutes) and resets after a success. Stronger against a patient child, more state and harder to explain.
3. Rate limit only (no lockout). Simplest, but a 4-digit PIN falls in about a day of patient guessing.

### 3. Where the kid-mode lock lives
1. Claims in the auth cookie itself (`fp:profile`, `fp:profile-household`), re-issued on switch and unlock. Deleting it signs the device out entirely (password needed), so it cannot be bypassed from the browser. Needs no new table.
2. A separate signed cookie next to the auth cookie. Easy, but deleting that cookie in the browser tools returns the device to the full adult session, so the lock is cosmetic.
3. Server-side device session table bound to the auth cookie. Revocable from other devices; needs a table, cleanup and more code than this task justifies.

### 4. What is attributed to a kid profile
(Likes always belong to the profile; this point is about the other actions.)
1. Also meal plan picks (`MealPlanEntry.PickedByProfileId`, as in the glossary's `pickedBy`). Check-offs and pantry confirmations keep pointing at the signed-in user.
2. Also check-offs and pantry confirmations. More faithful history, but two more columns and migrations on tables other tasks own.
3. Nothing; picks show the account holder only. No migration on `MealPlanEntries`, but "who picked what" is useless in a family app.

### 5. Who manages profiles and who may switch
1. Adult and Owner create, rename and delete profiles. An adult switching to a kid needs no PIN (but must have set one); a kid switching to another kid needs no PIN; only kid to adult needs the PIN.
2. Owner only manages profiles; switching as in 1. Fewer hands, but a second parent cannot add a child.
3. Same as 1, but every switch (including kid to kid) needs the PIN. Safer against siblings acting as each other, but breaks the "kid can switch in one tap" flow.

### 6. Which recipes a kid profile sees
Architect decisions already taken (not options): the kid UI is image-first with almost no text and no cooking time; the kid's core action is marking recipes they like (a per-profile list), and adults can see and use the likes.
1. All recipes, the ones tagged Barnevennlig listed first. Likes cover the whole recipe book; no server rule (the tag is a convention and may be sparse).
2. Only recipes tagged Barnevennlig, enforced by the server in kid mode. Safest feed for kids; a household that never tagged anything gives kids an empty app, and the server must filter every recipe read.
3. All recipes, no ordering. Simplest; kids scroll through everything.

### 7. Can kids suggest a dish for a specific day (optional, not in base scope)
1. No. Likes only; adults plan the week and read the likes. Matches the architect's wording.
2. Yes, a kid can propose a liked recipe for a day; adults accept (becomes a plan entry) or dismiss. Needs a new suggestion entity, adult review UI and a migration.
3. Yes, but only by setting a day on a like ("I want this on Friday"). Smaller, but mixes two ideas in one row.

## Recommendation
6. Option 1 (all recipes, Barnevennlig first; UI ordering only).
7. Option 1 (no suggestions). Revisit once likes are in use.
1. Option 1 (PIN per account). It matches the person who is signed in and works with external login.
2. Option 1 (4 to 8 digits, 5 failures lock for 15 minutes, 10 per minute per IP and user). The numbers sit in configuration. They mirror the existing login lockout (5 failures, 15 minutes).
3. Option 1 (claims in the auth cookie). The only choice where the lock cannot be removed from the browser without the password.
4. Option 1 (likes plus meal plan picks only). That is what the domain model names; extending to check-offs can be a later task if wanted.
5. Option 1 (Adult and Owner manage; PIN only from kid to adult).

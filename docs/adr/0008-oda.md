# ADR 0008: Oda integration

Status: proposed (T-001 Phase A done; verdict pending Phase B)

## Context
Original assumption (before T-001): no official public partner API; an unauthenticated search endpoint and an undocumented authenticated cart API.

Since 2026-10 Oda offers an official hosted MCP server, `https://oda.com/mcp` (info page `https://oda.com/mcp?demo&lang=en`, server version 2.0.0). Sign-in is the user's own Oda account in a browser; there is no API key. Raw evidence is in `spikes/oda/findings/`.

### Findings from public research (Phase A, 2026-10-31)
Auth discovery (standard MCP authorization, RFC 9728 + RFC 8414):
- Unauthenticated `POST /mcp initialize` returns `401` with `WWW-Authenticate: Bearer resource_metadata="https://oda.com/.well-known/oauth-protected-resource/mcp"`.
- Protected resource metadata: resource `https://oda.com/mcp`, authorization server `https://oda.com/o`, scope `mcp`, bearer in header only.
- Authorization server metadata (`https://oda.com/o/.well-known/oauth-authorization-server`): grant types `authorization_code` and `refresh_token`; response type `code`; PKCE `S256` only; token endpoint auth `none`, `client_secret_post`, `client_secret_basic`; endpoints `/o/authorize/`, `/o/token/`, `/o/revoke_token/`, **`/o/register/` (dynamic client registration supported)**; `client_id_metadata_document_supported: false`. No OpenID configuration.
- Not knowable without registering (checked in Phase B): redirect URI rules (loopback `127.0.0.1` accepted?), access/refresh token lifetime, refresh rotation, whether sessions (`Mcp-Session-Id`) are used.

Tools (public manifest `https://oda.com/mcp/manifest/`, saved as `findings/manifest.json`, schemas in `findings/tools.public-manifest.json`): 25 tools and resources. Relevant: `product_search` (up to 10 queries per call, page size up to 20), `get_cart`, `manipulate_cart`, `clear_cart`, `get_product_lists`, `create_product_list`, `manipulate_product_list`, `recipe_search`. Checkout and payment are not available; `get_cart` returns a `url` to review and pay in the shop.
- Product result fields: `id` (integer), `name`, `description`, `price` and `unitPrice` (strings), `unitName`, `brand`, `brandId`, `url`, `availability`. **No image URL and no SKU/EAN in the schema** (to be confirmed with real output in Phase B). The `url` is a shop page, so an image would need another source.
- Cart semantics: `manipulate_cart` takes operations on `productId`, `recipeId`, `productListId` or `orderNumber`; quantity is a **delta** (positive adds, negative removes, overshoot is safe, removal applies across all cart lines of that product). To reach a target, read `get_cart` first.

Terms (`https://oda.com/no/legal/betingelser/#bruk-av-oda-via-ki-assistenter-mcp`, excerpt in `findings/tos-mcp-section.md`): own shopping only; no extracting or collecting products, prices, recipes beyond one's own shopping; not on behalf of others, no resale or sharing access; no circumventing limits. Connected apps and assistants are expected ("provided by others than Oda"), their actions count as the user's own, access is revocable, Oda may restrict or close access. Privacy: `https://oda.com/no-en/legal/privacy-policy-global/`, `https://oda.com/no-en/account/privacy/`. Whether a family app may act as MCP client for a household is unclear: Q-024. Token storage beyond the spike: Q-025 (and T-099).

## Route options
a. **Foodplanner as MCP client for the household.** Per-member OAuth connection (DCR or one app client with our own redirect URI), search for matching products, fill the cart through `manipulate_cart`, return the cart `url`. Pros: best UX (one tap). Cons: stores third-party refresh tokens (T-099), ToS risk (Q-024), product matching quality unknown, no image or SKU in search results, we depend on a server we do not control (version 2.0.0, tool lists change).
b. **Assistant bridge.** Foodplanner only exposes the list: the existing text/share export (`IShoppingListExporter`, name `text`), or later its own MCP server with a read-only tool such as `get_shopping_list`. The user's own assistant (Claude, ChatGPT, ...), already connected to Oda by the user, searches and fills the cart. Pros: no Oda credentials in our system, fits the Oda ToS wording directly, nothing breaks when Oda changes its tools. Cons: needs an assistant, less deterministic, more steps for kids/non-technical family members.

## Decision
Verdict: **pending Phase B** (live sign-in, search quality, cart add and remove). Use the `IShoppingListExporter` adapter regardless; the text/share export is the guaranteed fallback. The leaning, to be confirmed: route b as the default, route a only if Oda answers Q-024 positively and Phase B shows good search quality.

## Consequences
Risks: ToS interpretation (Q-024), credential storage (Q-025, T-099), dependency on a third-party hosted server, no barcodes/images. Contact Oda about partner access remains advisable. Endpoints relied on will be listed here when the verdict is set.

# ADR 0008: Oda integration

Status: accepted (T-001 Phase A and B done, 2026-11-19). Verdict: fragile; see Decision. Updated 2026-11-20 with the architect's answers to Q-024, Q-025, Q-032 and Q-033: route a, session-only (see "Decision (2026-11-20)").

## Context
Original assumption (before T-001): no official public partner API; an unauthenticated search endpoint and an undocumented authenticated cart API.

Since 2026-10 Oda offers an official hosted MCP server, `https://oda.com/mcp` (info page `https://oda.com/mcp?demo&lang=en`, server version 2.0.0 in Phase A, 2.3.0 in Phase B). Sign-in is the user's own Oda account in a browser; there is no API key. Raw evidence is in `spikes/oda/findings/`.

### Findings from public research (Phase A, 2026-10-31)
Auth discovery (standard MCP authorization, RFC 9728 + RFC 8414):
- Unauthenticated `POST /mcp initialize` returns `401` with `WWW-Authenticate: Bearer resource_metadata="https://oda.com/.well-known/oauth-protected-resource/mcp"`.
- Protected resource metadata: resource `https://oda.com/mcp`, authorization server `https://oda.com/o`, scope `mcp`, bearer in header only.
- Authorization server metadata (`https://oda.com/o/.well-known/oauth-authorization-server`): grant types `authorization_code` and `refresh_token`; response type `code`; PKCE `S256` only; token endpoint auth `none`, `client_secret_post`, `client_secret_basic`; endpoints `/o/authorize/`, `/o/token/`, `/o/revoke_token/`, **`/o/register/` (dynamic client registration supported)**; `client_id_metadata_document_supported: false`. No OpenID configuration.
- Not knowable without registering (checked in Phase B): redirect URI rules (loopback `127.0.0.1` accepted?), access/refresh token lifetime, refresh rotation, whether sessions (`Mcp-Session-Id`) are used.

Tools (public manifest `https://oda.com/mcp/manifest/`, saved as `findings/manifest.json`, schemas in `findings/tools.public-manifest.json`): 25 tools and resources. Relevant: `product_search` (up to 10 queries per call, page size up to 20), `get_cart`, `manipulate_cart`, `clear_cart`, `get_product_lists`, `create_product_list`, `manipulate_product_list`, `recipe_search`. Checkout and payment are not available; `get_cart` returns a `url` to review and pay in the shop.
- Product result fields: `id` (integer), `name`, `description`, `price` and `unitPrice` (strings), `unitName`, `brand`, `brandId`, `url`, `availability`. **No image URL and no SKU/EAN in the schema** (to be confirmed with real output in Phase B). The `url` is a shop page, so an image would need another source.
- Cart semantics: `manipulate_cart` takes operations on `productId`, `recipeId`, `productListId` or `orderNumber`; quantity is a **delta** (positive adds, negative removes, overshoot is safe, removal applies across all cart lines of that product). To reach a target, read `get_cart` first.

Terms (`https://oda.com/no/legal/betingelser/#bruk-av-oda-via-ki-assistenter-mcp`, excerpt in `findings/tos-mcp-section.md`): own shopping only; no extracting or collecting products, prices, recipes beyond one's own shopping; not on behalf of others, no resale or sharing access; no circumventing limits. Connected apps and assistants are expected ("provided by others than Oda"), their actions count as the user's own, access is revocable, Oda may restrict or close access. Privacy: `https://oda.com/no-en/legal/privacy-policy-global/`, `https://oda.com/no-en/account/privacy/`. Whether a family app may act as MCP client for a household was raised as Q-024; token storage as Q-025. Both were answered on 2026-11-20 (see Decision).

## Route options
a. **Foodplanner as MCP client for the household.** OAuth sign-in to Oda, search for matching products, fill the cart through `manipulate_cart`, return the cart `url`. Pros: best UX (one tap). Cons as first assessed: stored third-party refresh tokens (T-099) and ToS risk (Q-024), both since resolved by the session-only variant below; product matching quality, no image or SKU in search results, and a server we do not control (version 2.0.0, tool lists change) remain.
b. **Assistant bridge.** Foodplanner only exposes the list: the existing text/share export (`IShoppingListExporter`, name `text`), or later its own MCP server with a read-only tool such as `get_shopping_list`. The user's own assistant (Claude, ChatGPT, ...), already connected to Oda by the user, searches and fills the cart. Pros: no Oda credentials in our system, fits the Oda ToS wording directly, nothing breaks when Oda changes its tools. Cons: needs an assistant, less deterministic, more steps for kids/non-technical family members.

### Findings from the live run (Phase B, 2026-11-19)
Summary in `spikes/oda/findings/phase-b.md`; schemas in `findings/tools.json`; search table in `findings/search-quality.md`.
- OAuth with dynamic client registration, PKCE and a loopback redirect worked in a browser sign-in; in the spike the token stayed in user secrets and all later calls authenticated. **Token refresh was not tested** (lifetime unknown). The product keeps no token at all (Decision 2026-11-20), so refresh is not needed.
- Server "Oda MCP Server" 2.3.0, 25 tools, same set as the public manifest (the version changed from 2.0.0 within weeks).
- Product fields: `id`, `name`, `description`, `price`, `unitPrice`, `unitName`, `brand`, `brandId`, `url`, `availability`. No image, no SKU/EAN.
- Search for basic nb names gives relevant top hits, with weaknesses: "karbonadedeig" top hit is kjøttdeig, "Nøytral olje" includes olivenolje, "egg" and "kyllingfilet" return several pack sizes (pack-size choice needed).
- Cart: add of one product moved the total by exactly its search price; `clear-test-items` restored the cart exactly and left other lines unchanged. Open observation: the cart line amount (61.40) did not match the search price (44.90) for the added product; `get_cart` `total_breakdown` (discounts) not examined. The cart reports availability problems as a validation message that blocks checkout.
- No offer/campaign field on search, `likely_to_buy` or `unique_for_you` results; offers are not reachable through MCP product data (relevant to T-107).

## Decision
Verdict: **fragile**. Technically a direct client works: sign-in, search and cart add/remove all worked end to end, and the cart can be reverted cleanly. It is fragile because:
- the legal basis was unclear (Q-024: terms say own shopping only, not on behalf of others); resolved 2026-11-20, see below;
- it needed stored third-party refresh tokens (Q-025, T-099) and refresh is untested; resolved 2026-11-20 by keeping no token;
- the server version already changed (2.0.0 to 2.3.0) and we do not control it;
- search results lack image and SKU/EAN, so matching to our structured ingredients relies on name text and needs pack-size rules; some names mis-rank;
- there is no offer data.

Original decision (2026-11-19): keep the `IShoppingListExporter` adapter and the text/share export as the guaranteed fallback, keep route b (assistant bridge) as the default, and allow route a only after Q-024 and Q-025 are answered.

### Decision (2026-11-20, architect)
Route a, **session-only**, is the Oda route. The text/share export (`IShoppingListExporter` `text`) stays as the fallback, and the assistant bridge stays possible but is not the default.
- **One shared household Oda account** (Q-024). The household already shares one Oda account, so Foodplanner may fill that account's cart for the household. A written confirmation from Oda is not required.
- **No standing connection, nothing stored** (Q-025). An Adult taps "Add to Oda cart" on the shopping list and signs in to Oda at that moment. In one request Foodplanner exchanges the code, searches, fills the cart and revokes the token at `/o/revoke_token/` (also on error and cancel). The token lives only in memory for that request and is never persisted or logged. T-099 is not needed for Oda.
- **Product choice** (Q-032). T-053 stores no Oda product id and adds the first available hit, one pack per item. The household does final swaps and fixes in Oda. Later, T-114 prefers what the household usually buys (its own Oda purchase history, read during the same connection, nothing stored), and T-052 lets an Adult pick a preferred product per ingredient (only the Oda product id is stored).
- **OAuth flow state across replicas** (Q-033). The PKCE verifier and state travel in a short-lived (10 minutes) encrypted `__Host-` cookie. A shared, persisted Data Protection key ring is required before more than one API replica runs. That is T-016 (persist Data Protection keys in Azure), also needed by the auth cookie.
- **Client and redirect.** One app-wide public client per environment (token endpoint auth `none`), with a redirect URI on Foodplanner's own origin. That Oda accepts a non-loopback redirect URI is unverified; T-053 checks it first.
- **Terms.** Searches cover only the items being added, and nothing from Oda is collected or kept beyond the request (except the Adult-chosen product id in T-052). Oda's usage limits are respected.
- The verdict stays **fragile** for the remaining reasons: a server we do not control, no image or SKU/EAN, name-based matching, and no offer data.

Spec: `docs/specs/T-053-oda-cart-session.md`.

### Endpoints and tools relied on
- OAuth discovery: `/.well-known/oauth-protected-resource/mcp` (RFC 9728) and `/o/.well-known/oauth-authorization-server` (RFC 8414).
- Dynamic client registration `/o/register/`, authorize `/o/authorize/`, token `/o/token/` (code + PKCE S256). The refresh_token grant is declared by Oda but not used, since the product keeps no token. In the spike the connection was revoked by hand in Oda privacy settings; the product revokes at `/o/revoke_token/` (unverified until T-053).
- MCP `https://oda.com/mcp` tools: `product_search`, `get_cart`, `manipulate_cart` (also `likely_to_buy` and `unique_for_you`, read-only, for the T-107 check).
- Not used: `clear_cart`, product lists, `recipe_search`, orders and delivery tracking, addresses and delivery slots. Checkout/payment does not exist in MCP; the user pays via the cart `url`.

## Consequences
Risks: the household-account reading of Oda's terms is the architect's call (Q-024) and Oda may restrict access; dependency on a third-party hosted server whose tools change; unverified redirect URI and revoke behaviour (checked in T-053); the shared Data Protection key ring for more than one replica (Q-033); no image or SKU/EAN, no offer data (T-107 must use the assistant bridge or drop offers). Contacting Oda about partner access remains advisable. Any future direct client must treat tool schemas as unstable (contract tests against `tools.json`-style snapshots) and surface cart validation messages.

## Goal
Reported by the architect on 2026-10-27: after switching language in the app, some text stays in the old language. Find every place and fix it so a language switch updates all translatable text without a manual reload.

## Context
Read CLAUDE.md, docs/questions/Q-013.md, web/README.md (Internationalisation, PWA/service worker), docs/domain.md (catalog translations T-039). Likely causes to check (not confirmed):
- UI strings rendered outside the t() re-render path (module-level constants, memoised values, strings computed once).
- Catalog names (ingredients, units, tags, shopping list items, recipe ingredient names) come from the API per Accept-Language; screens already loaded don't refetch when the locale changes.
- The service worker (T-041) caches recipe/tags GETs by URL only, so a cached response in the old language can be served after a switch (cache key must include the language, or the runtime cache must be cleared/bypassed on switch).
- Intl date/number formatting created once with the old locale; `<html lang>`; document title; the web app manifest name.
Not a bug, by design (Q-013): household-entered text (recipe titles, steps, own ingredients and tags, manual list items, imported recipe text) stays as typed.

## Out of scope
Translating household-entered or imported text; new locales.

## Acceptance criteria
- [ ] Reproduce first and list every screen and string that did not switch (before/after table in the task report)
- [ ] After a language switch, all UI text and all catalog-derived names update on every screen without reload, online and with the service worker active
- [ ] Service worker runtime cache cannot return a response in the wrong language (test)
- [ ] A Playwright test switches nb ⇄ en on each main screen (recipes, recipe detail, plan, shopping, household, import, cooking mode) and asserts a known UI string and a known catalog name change
- [ ] Vitest coverage for any refetch-on-locale-change logic

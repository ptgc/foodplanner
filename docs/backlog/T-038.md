## Goal
Every user-facing text in the web app is translatable (Q-013). Code and keys are English; English is the fallback; locales nb and en for now. If a translation is missing in both, the short English placeholder text is shown. Convert all existing screens (shell, login, home, shopping list) and make it the pattern every later screen copies.

## Context
Read CLAUDE.md, ADR 0001 and docs/questions/Q-013.md. Pick a small, maintained library (or a tiny in-house module if it is clearly simpler); pin exact versions. Locale choice: browser language first (nb/no/nn → nb), user override stored per device; dates and numbers formatted with Intl for the active locale. API error messages: map ProblemDetails `type` codes to translated messages in the client rather than translating server text.

## Out of scope
Translating catalog data (T-039). More locales. Server-rendered text.

## Acceptance criteria
- [ ] No hard-coded user-facing string remains in web/app (a lint rule or test fails on literal JSX text outside the translation files)
- [ ] nb and en message files; a missing nb key falls back to en, a key missing in both shows the short English placeholder; tested
- [ ] Language switch in the shell (44px target, 390px), remembered per device, default from the browser language
- [ ] ProblemDetails `type` codes used by existing screens map to translated messages
- [ ] Existing Vitest and Playwright tests pass in both locales (Playwright runs at least one spec in nb)

## Verification
`./scripts/verify.sh` green, plus the checks above evidenced with command output.

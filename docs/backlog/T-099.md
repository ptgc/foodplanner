# T-099: Store third-party credentials and tokens encrypted

## Goal
Architect decision 2026-10-29: when the app holds real credentials for other services (e.g. a household's Oda sign-in/token for the cart integration, T-053), they must be safe. Locally, user secrets are fine for development (T-001 spike). For the app itself: never store a password; store only the tokens a provider issues (OAuth/MCP), encrypted at the application level per household, with keys outside the database.

## Context
Read ADR 0008 (Oda, after T-001), T-016 (Data Protection keys in Azure), CLAUDE.md rule 7 (Key Vault + managed identity), docs/domain.md tenancy. Options to decide (raise a question first): ASP.NET Core Data Protection with keys in Blob + Key Vault (T-016) vs. Key Vault keys directly (envelope encryption) vs. SQL Always Encrypted columns. Azure SQL already encrypts the whole database at rest (TDE); this task is about column/application-level protection so a DB dump or a support view never exposes a usable token. Also: token refresh and revocation, the user can disconnect, deleting a household deletes its tokens, tokens never in logs or API responses.

## Acceptance criteria
- [ ] Decision recorded (question file / ADR) before implementation
- [ ] Tokens encrypted at rest with keys outside the database; tenant entity in the isolation suite
- [ ] Never returned by the API, never logged (test); disconnect and household deletion remove them
- [ ] Key rotation documented

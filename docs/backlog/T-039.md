## Goal
Seeded global catalog rows (ingredients, units, tags) carry names in nb and en (Q-013). The API returns the name for the request's language (Accept-Language, nb or en; default en) and falls back to en, then to the stable English key. Text a household types itself (own ingredients, tags, recipe titles, manual list items) is stored and shown as typed.

## Context
Read CLAUDE.md, docs/domain.md (catalog, seed ids are UUIDv5 from stable ASCII keys), docs/questions/Q-013.md. Keep seed data in one file per type; adding a locale must not require a schema change (e.g. a translation table keyed by entity id + locale, or per-locale columns only if you can justify it). Sorting and search use the requested locale (nb-NO collation rules for nb). The shopping list generator and duplicate-name checks must keep working with both names.

## Out of scope
UI text (T-038). More locales. Translating household-entered text.

## Acceptance criteria
- [ ] Every seeded ingredient, unit and tag has nb and en names; seed is idempotent and ids are unchanged
- [ ] API responses use Accept-Language (nb/en) with fallback en → key; tested for ingredients, tags, units, recipe detail ingredient names and shopping list items
- [ ] Ingredient search matches in the requested language; duplicate-name check covers both languages for global rows
- [ ] Household-entered names are returned unchanged in both languages
- [ ] Isolation suite and catalog harness still pass; migration applies on a fresh DB and on the local DB

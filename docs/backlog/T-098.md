## Goal
Architect decision 2026-10-29: T-097 worked around the memory problem by splitting Api.Tests into three processes (peak 837 MB each). In one process the working set grows steadily with the number of tests run (about 1.6 GB peak for ~1100 Api tests, even with `--max-threads 2`; GC conserve-memory settings and clearing SqlClient pools per class did not help). That points to something kept alive per test or per test class: a likely memory leak in the test setup (or in the app). Find the cause and fix it, so one process stays flat.

## Context
Read T-097 (its report in the commit body of 1a03c17), tests/Api.Tests (WebApplicationFactory / host fixtures, SqlServerFixture, Azurite, per-class hosts, HttpClients, SignalR test connections), the app's singletons and static caches (e.g. hub groups, rate limiters, data protection, image processing with NetVips, EF model/compiled query caches, IMemoryCache), scripts/verify.sh. Suspects to check (not confirmed): a new WebApplicationFactory/host per class that is never disposed; hosted services or timers keeping hosts alive; SignalR connections or HubConnection objects not disposed; NetVips native memory; EF Core service provider caching (a new internal service provider per DbContext options instance); static event handlers or loggers.

Use a memory profile (e.g. `dotnet-counters`, `dotnet-gcdump` before/after N test classes, compare retained types and their roots) rather than guessing; record the findings.

## Out of scope
Changing what is tested.

## Acceptance criteria
- [ ] Root cause found and evidenced (gcdump diff or equivalent: retained types, counts, roots)
- [ ] Fix in test setup and/or app code; if the app itself leaks, a regression test or note
- [ ] One Api.Tests process stays roughly flat: peak working set measured before/after for the whole Api.Tests run in one process
- [ ] If memory is now flat, decide with the architect whether verify.sh goes back to one test pass in low-memory mode (keep T-097's override)

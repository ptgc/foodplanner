# T-072: Set the password at confirm time, expire unconfirmed accounts

Status: in-progress
Milestone: L2
Agent: implementer-backend
Depends on: T-009, T-028, T-038
Migration: no
Branch: task/T-072-set-password-at-confirm-time

## Goal
Close the pre-account-hijack and squatter problems from Q-011. Register records only the email and sends a link; the link opens a "set your password" step; only then does the account get a password and become confirmed. Unconfirmed accounts are removed after the confirmation window so the address frees up. Includes the small frontend screens (register, set password) using T-038 translatable text.

## Context
Read CLAUDE.md, the T-009 spec, docs/questions/Q-002.md and Q-011.md, ADR 0004. Responses stay uniform (no account enumeration). Rate limits and antiforgery as in T-009. The seeded local admin (T-029) is created confirmed and is unaffected.

## Out of scope
Password reset and change, Google login (T-010), email provider (Q-007).

## Acceptance criteria
- [ ] Register stores no password; confirm-with-password sets it and confirms in one step; a reused or expired link is rejected
- [ ] An attacker who registered first can never end up controlling the account the owner confirms (test of the Q-011 race in both orders)
- [ ] Unconfirmed accounts older than the confirmation window are removed by a background job (fake clock test); the address can then be registered again
- [ ] Register and set-password screens at 390px, translatable, with Playwright coverage using the recording email sender in Development
- [ ] T-009 tests updated; responses stay identical for new and existing addresses

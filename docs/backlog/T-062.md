## Goal

## Context
Read CLAUDE.md, docs/domain.md and relevant ADRs in docs/adr/.

## Implementation notes
- `.claude/hooks/guard-bash.sh` (PreToolUse on Bash) checks the full command text: protected-branch pushes, force-push and remote deletes, `gh pr merge`, secrets and rulesets, Azure and deploy tooling that mentions prod, and reads of `.env` and key material. It denies, or asks for approval on Azure changes, `azd`, `docker push` and `gh workflow run`. `.claude/hooks/test-guard-bash.sh` has 76 cases; run it after changing the hook.
- `.claude/settings.json` adds deny rules (first-form defence in depth, including `Read` rules for `.env` and key files) and narrow allow rules. Pushes are allowed only to `task/*` and `dev`.
- Verified: the hook test suite; in a fresh headless session `cat .env` was blocked by the hook and the Read tool was denied on `.env`.
- Not verified: the allow rules. Claude Code ignores a project's `permissions.allow` until the folder is trusted (interactively once, or `hasTrustDialogAccepted` in `~/.claude.json`), so unattended runs prompt for every command until then. Tick the last box after trusting the folder and watching a run.
- Limits: the hook is a guardrail, not a security boundary. It cannot see through eval, base64, variables or scripts that run git or az themselves. Real enforcement of the branch model is the GitHub rulesets in T-064; real enforcement of prod is that no agent holds prod credentials.
- Agents can still edit `.claude/settings.json` and the hook. Protecting them needs CODEOWNERS or managed settings; raise a question if you want that.

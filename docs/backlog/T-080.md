## Goal
Found on 2026-10-27 while adding a recipe from a phone photo: a 2 MB JPEG upload to PUT /api/households/{h}/recipes/{r}/image through http://localhost:3000 returns 413 from nginx, because web/nginx.conf sets no client_max_body_size (nginx default 1 MB). The API itself allows 10 MB (Images:MaxUploadBytes). Every normal phone photo fails in the containers; T-022/T-024/T-025 tests only used small images, so nothing caught it.

## Context
Read web/nginx.conf, docs/domain.md (images T-022: MaxUploadBytes), web/README.md, the recipe edit form's client-side size check (T-025). Keep limits consistent in one place where possible.

## Out of scope
Changing the API limit; client-side resizing (could be a later improvement).

## Acceptance criteria
- [ ] nginx allows request bodies up to the API image limit (10 MB + multipart overhead) on the image upload route (or /api/ generally — decide and document); other routes keep a sensible small limit
- [ ] A body over the limit gets a clean 413 that the web app shows as the translated "image too large" message (not a generic error)
- [ ] Playwright test uploads a realistic ~3 MB JPEG through http://localhost:3000 and sees the picture; a ~12 MB file shows the translated too-large message
- [ ] Vite dev path checked too (no proxy limit surprise)

## Verification
`./scripts/verify.sh` green, plus the checks above evidenced with command output.

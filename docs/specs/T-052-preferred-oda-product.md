# Spec: Preferred Oda product per ingredient (T-052)
## Goal
After "Add to Oda cart", an Adult sees what was put in the cart, and for a line can say "use this product for this ingredient from now on" by picking one of the top Oda hits that the same fill returned. The next fill adds that product from the start. The household can see and clear its choices later without any Oda connection.

Decision record: architect, 2026-11-22 (task file T-052), with [Q-032](../questions/Q-032.md) (answered 2026-11-20): only the Oda product id per (household, ingredient) is stored, set by an Adult; no name, price, brand or search result. Priority in the fill: the household's own pick (this task), then purchase history ([T-114](T-114-oda-usually-bought.md)), then the first available hit. Base: [T-053](T-053-oda-cart-session.md). No second Oda sign-in is ever needed to pick.

This spec narrows two T-053 statements, as Q-032 allows: "no Oda product ids in the database" and "no migration" now apply except for the one preference table below.

## Users & roles
| Action | Anonymous | Non-member | Child member | Kid-mode session | Adult | Owner |
|---|---|---|---|---|---|---|
| `GET /oda-preferences` (list) | 401 | 403 | 403 | 403 | yes | yes |
| `PUT /oda-preferences/{ingredientId}` (set) | 401 | 403 | 403 | 403 | yes | yes |
| `DELETE /oda-preferences/{ingredientId}` (clear) | 401 | 403 | 403 | 403 | yes | yes |
| Fill reads the household's preferences (`oda/cart`) | as T-053 | | | | yes | yes |

- All three endpoints carry policies `HouseholdAdult` and `FullSession` (T-011, T-105), no role is read in endpoint code (rule 2). Child members (also with their own login) and kid-mode sessions get 403 ProblemDetails (`forbidden` or `kid-mode`); a non-member gets 403. Nothing here calls Oda.
- Tenancy: `PreferredOdaProduct` is an `ITenantEntity`. Every read and write goes through the tenant-filtered set of the household in the route. An Adult of household A calling under B gets 403; B's preferences are never listed, read by A's fill or changed. An `ingredientId` of another household (or an unknown one) is resolved through the filtered `Ingredients` set and answered `404 ingredient-not-found` (the same answer for both, Q-012 rule).

## Behaviour

### What is stored
`PreferredOdaProduct` (Domain, `ITenantEntity`, own Guid key, no navigations): `HouseholdId`, `IngredientId` (global or the household's own ingredient), `OdaProductId` (`bigint`, Oda's integer product id, > 0), `CreatedAt`, `UpdatedAt` (from `Entity`). Unique `(HouseholdId, IngredientId)`: one product per ingredient, a new pick replaces the old. Nothing else: no name, brand, price, URL, search hit or "when seen". The same Oda product may be the pick of several ingredients. At most 500 rows per household (`409 oda-preference-limit` beyond that). Migration `AddPreferredOdaProducts` (`Migration: yes`: check the backlog for another migrating task before starting). Cascade only Household -> row; the Ingredient FK is NO ACTION.
Ingredient merge (T-079): when the source ingredient has a row and the target has none, the row moves to the target; when both have one, the target's row stays and the source's is removed. Deleting an ingredient: see [open question](#open-questions) 2.

### Endpoints
Under `/api/households/{householdId}/oda-preferences`, `MapOdaPreferenceEndpoints`; unsafe methods are under the antiforgery group (T-009).
- `GET`: `[{ ingredientId, ingredientName, setAt }]` ordered by `ingredientName` (request language, the `nb-NO` comparison used by the shopping list), `setAt` = `UpdatedAt`. No product name or id is returned: Foodplanner does not have them (the id is stored but meaningless to a person). Empty household: `[]`.
- `PUT /{ingredientId}` with `{ "odaProductId": 12345 }`: creates or replaces the row, 200 `{ ingredientId, ingredientName, setAt }` (also for a repeat with the same id). `odaProductId` missing, not an integer or <= 0: 400 ValidationProblem on `odaProductId`. Foodplanner cannot check that the id exists at Oda (no Oda call here); a wrong id is harmless: it matches no hit and the fill falls back (below). A lost unique-index race is retried once, then `409 oda-preference-conflict`.
- `DELETE /{ingredientId}`: `204`, idempotent (also when there is no row). Ingredient unknown or other household's: 404 as above.
- Tracked EF saves only (no `ExecuteUpdate`/`ExecuteDelete`). `ICurrentUser` is never recorded: no "set by".

### How the fill uses the preference (changes `oda/cart`)
- Before the fill the endpoint reads the household's preferences through the filtered set into an in-memory map `ingredientId -> odaProductId` and passes it to the pure Domain matcher. `CartLine` gains `IngredientId` (`Guid?`, null for a manual item, which can have no preference) and `CartSourceItem` the same.
- Per item, candidates are the item's available search hits in Oda's rank order. Order of rules: (1) the hit whose id equals the preferred id; (2) the T-114 rule (first available usual product); (3) the first available hit. Exact id match only; the preferred product is found only among the item's search hits (no product-by-id tool exists at Oda; see [open question](#open-questions) 1).
- When the item has a preference that cannot be used, the line is still added by rule 2 or 3 and carries `preferenceProblem`: `unavailable` (the id is among the hits but not available now, e.g. sold out) or `not-found` (the id is not among the hits: gone from the assortment, or ranked outside the page). If nothing can be added the item is `notAdded` as in T-053 and the preference is not mentioned.
- A preference that cannot be used is never changed or deleted by the fill (a product is often only sold out for a few days). The household clears or replaces it.
- Call count: unchanged from T-053/T-114. The `likely_to_buy` call is skipped when every item with a hit is decided by a preference. Nothing is searched by id; no extra Oda tool is used.

### Result shape (changes `oda/cart` 200; additive, TS client regenerated)
Each `added[]` line becomes `{ itemId, name, productName, quantity, source, ingredientId, productId, hasPreference, preferenceProblem, alternatives }`:
- `source`: `preferred` | `usually-bought` | `first-hit`.
- `ingredientId`: the item's ingredient or null (manual item); `productId`: the added product's Oda id (integer).
- `hasPreference`: the household has a preference for that ingredient (used or not).
- `preferenceProblem`: `null` | `unavailable` | `not-found`.
- `alternatives`: empty when `ingredientId` is null; otherwise up to 5 entries `{ productId, productName, isAdded, isPreferred }` taken from the item's search hits of this same fill, available ones only, in Oda's rank order. The added product is always included (replacing the last entry if it was ranked beyond the 5th), so `isAdded` is true exactly once. `isPreferred` marks the hit equal to the stored id. A line with fewer than 2 alternatives and no preference offers no picker.
- Names and ids in `alternatives` exist only in this response and in the page's React state; they are not stored by the server or browser. The `added` list of a 502 `oda-unavailable` body carries `source` but no `alternatives` (the picker is for a finished fill).
- `usuallyBought` of T-114 is unchanged.

### Picking on the Oda result screen (T-054 screens, Adult only, changed in this task)
- On each added line with alternatives, a button "Choose another product" / "Velg et annet produkt" (min height 44px) opens an inline list under the line (a bottom sheet is not required). Each alternative is one full-width row (min height 44px, the product name wraps, nothing clips at 390px) with the current product marked. A row that is not the preferred one has "Use this next time" / "Bruk denne neste gang"; tapping it calls `PUT /oda-preferences/{ingredientId}`, then the row shows "Saved for next time" and the line label becomes "Your Oda choice" / "Ditt Oda-valg". A line with `hasPreference` also has "Remove choice" / "Fjern valget" (calls `DELETE`).
- Picking never changes the Oda cart: a note on the list says the cart is not changed and swaps are done in Oda. The note also says what is stored: only which product this ingredient should use (no sign-in kept).
- Labels on added lines: `preferred` shows "Your Oda choice", `usually-bought` shows the T-114 label, and `preferenceProblem` shows one line ("Your choice was sold out" for `unavailable`, "Your choice was not found at Oda" for `not-found`; nb + en) together with the product that was added instead.
- Failure of a PUT or DELETE: an inline error line from the ProblemDetails (403, 409, 429, network), the list stays open, the cart result is unaffected. Offline: the buttons are disabled with a note.
- The callback page still reads the result once and never retries `oda/cart`; picking calls only the Foodplanner endpoints above.

### Seeing and clearing choices later (no Oda connection)
- A page `/shopping/oda-choices` (Adults only: the link "Your Oda choices" / "Dine Oda-valg" sits on the shopping page below the Oda button and on the result screen; hidden for Child members and in kid mode; a Child opening the address sees a short "only adults" note, the API answers 403).
- It reads `GET /oda-preferences` and lists one row per ingredient: ingredient name, the fixed text "Your Oda choice" / "Ditt Oda-valg" and "set on <date>", plus "Clear" (44px). Product names are not stored, so none is shown; the page says the product is shown the next time the cart is filled, where it is marked as "Your Oda choice". Clear calls `DELETE` and removes the row with a short confirmation; there is no "clear all" and no way to set a choice here (picking needs a fill, which is the only time names are available). Empty state: one sentence explaining how to choose a product after "Add to Oda cart". Works at 390px, nb + en, offline shows the last read with buttons disabled.
- Realtime sync of choices between devices is not needed (a reload shows the current state).

## Out of scope
Using purchase history to guess a product (T-114); prices, offers (T-107); storing any name, price, brand, image, URL, hit list or "usually bought" data; a second sign-in or any Oda connection for picking or for the choices page; setting a choice by typing a product name or searching Oda from the choices page; choosing pack size or quantity; picking for manual list items; automatic clearing of stale choices; "clear all"; changing the Oda cart from Foodplanner after the fill; per-member choices (a choice is the household's); sync of choices over SignalR.

## Open questions
Each is answered by the architect when approving the spec. The criteria above assume the recommendation.
1. **How is the preferred product found at fill time, given Oda has no product-by-id tool?** Options: (a) match the stored id only among the item's search hits (page of `Oda:SearchPageSize`), report `not-found` otherwise; (b) add the stored id straight to the cart without relying on a hit (no name or availability known, so the line name must come from the cart response, and a refused line needs a second add call for the fallback, which breaks the "never repeat" and small-call-count rules); (c) as (a) with a larger search page (see T-114 open question 1, recommended size 10) so the picked product, taken from the same query, stays in range even when ranks shift. Recommendation: (c). It keeps the fill simple and the call count unchanged, and the household's choice came from that same query. If rank drift still loses a choice, the line says `not-found` and the household picks again.
2. **What happens to a preference when its ingredient is deleted?** Today deleting an ingredient is refused with `409 ingredient-in-use` while something references it. Options: (a) a preference counts as a reference and blocks the delete (the user must clear it on the choices page first); (b) the preference is removed together with the ingredient in the same save; (c) leave an orphan row (not possible with the foreign key). Recommendation: (b): a preference is a convenience, not something to protect, and blocking the delete over it would be confusing; the delete stays refused while recipes, lists or pantry still use the ingredient.
3. **Where may a choice be changed besides the result screen?** The decision says "on the Oda result screen". Product names exist only during a fill, so the choices page can only clear. Options: (a) as written (set only on the result screen, clear on both); (b) also offer "Replace" on the choices page that starts a new "Add to Oda cart" fill (it would add to the cart again, so not wanted); (c) a separate session-only "pick product" flow with a search while connected (a second sign-in, extra searches, against the architect's decision). Recommendation: (a).
4. **Cap on the number of choices per household** (500 here, a guard against abuse, not a product number). Options: (a) 500; (b) none; (c) a configuration value `Oda:MaxPreferences`. Recommendation: (a); say so if another number is wanted.

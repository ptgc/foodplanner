# Spec: Sync with Oda, set up preferred products in one go (T-130)
Status: approved by the architect 2026-11-24 (Q-039 and Q-040 answered option 1)
## Goal
An Adult or Owner taps "Sync with Oda", signs in to the household's shared Oda account once, and gets one review list for the ingredients used in the household's recipes: what the household usually buys (pre-ticked), a suggestion (unticked), and what was not found. Confirming saves the ticked rows as T-052 preferred products (Oda product ids only). The Oda connection is session-only and is closed (revoked) before the review is shown; nothing but the confirmed product ids is stored.

Decision record: architect request and decisions 2026-11-22 (task file T-130): only ingredients used in recipes plus opt-in staples; existing choices are never overwritten unless ticked; `likely_to_buy` only, no order history; batched searches within Oda usage limits. Base specs: [T-053](T-053-oda-cart-session.md) (session-only connection, OAuth/PKCE, revoke, flow cookie), [T-114](T-114-oda-usually-bought.md) (`likely_to_buy`, matching), [T-052](T-052-preferred-oda-product.md) (`PreferredOdaProduct`, endpoints, choices page). ADR 0008 (Decision 2026-11-20), [Q-024](../questions/Q-024.md), [Q-025](../questions/Q-025.md), [Q-032](../questions/Q-032.md) and [Q-033](../questions/Q-033.md) apply unchanged. Numbers below marked (Q-039) follow that question's answer (option 1, architect 2026-11-24).

## Users & roles
| Action | Anonymous | Non-member | Child member | Kid-mode session | Adult | Owner |
|---|---|---|---|---|---|---|
| `POST oda-sync/start` | 401 | 403 | 403 | 403 | yes | yes |
| `POST oda-sync/preview` | 401 | 403 | 403 | 403 | yes | yes |
| `POST oda-sync/review` | 401 | 403 | 403 | 403 | yes | yes |
| `PUT oda-preferences` (bulk save) | 401 | 403 | 403 | 403 | yes | yes |
| Existing T-052 endpoints, T-053 cart endpoints | unchanged | | | | | |

- All three new endpoints carry policies `HouseholdAdult` and `FullSession` (T-011, T-026/T-105); no endpoint code reads a role (rule 2). A Child member (also with their own login) and any kid-mode session get 403 ProblemDetails (`forbidden` or `kid-mode`), and no call to Oda is made. The button and the screen are hidden for them; a Child opening the address sees the same short "only adults" note as the choices page.
- Tenancy: the ingredients, existing choices and recipes are read through the tenant-filtered sets of the household in the route. An Adult of A calling under B gets 403; B's recipes, ingredients and choices are never read, searched or written. Bulk save resolves every ingredient id through the filtered `Ingredients` set; another household's id and an unknown id give the same `404 ingredient-not-found` (Q-012 rule). The flow cookie is bound to household, user and kind (below).
- The Oda account is the household's one shared account, as in T-053: Foodplanner does not know or link which account it is. The review screen is shown to the person who signed in.

## Behaviour

### Flow
1. **Where.** A button "Sync with Oda" / "Synkroniser med Oda" is on the page `/shopping/oda-choices` (T-052; the "Your Oda choices" page, Adults only), and the shopping page's "Your Oda choices" link leads there. T-131's "Kom i gang" step links to the same page. Hidden when Oda is not configured (`Oda:ClientId` empty) and for Child and kid mode. Offline: disabled with a note.
2. **Confirm.** The button opens a short confirmation (same pattern as T-054): how many ingredients will be searched (the count comes from `preview`, step 3; it is asked when the dialog opens and again on every toggle, and `start` is not), that Oda opens for sign-in, that nothing is added to the cart or ordered, that only the products the user confirms are kept (their numbers only), and two checkboxes, both off by default: "Also staples (salt, pepper, flour, ...)" and "Also check ingredients that already have a choice".
3. **Preview, then Start.** `POST /api/households/{h}/oda-sync/preview` `{ includeStaples, includeExisting, offset }` returns `{ ingredientCount, notCheckedCount }` (409 `oda-sync-nothing-to-sync` when empty, 404 `oda-not-configured`). It uses the same selection as `start`, sets no cookie, builds no PKCE address and makes no call to Oda; policies `HouseholdAdult` and `FullSession`, antiforgery, and its own lenient limit `oda-preview` (60 a minute per user, `RateLimiting:OdaPreview`), not the `oda-action` limit. `start` is called exactly once, on Confirm (Confirm is disabled while it runs); its response URL is the one the browser goes to, so a flow cookie can never hold the options of an older toggle. `POST /api/households/{h}/oda-sync/start` `{ confirmed: true, includeStaples, includeExisting, offset }` makes no call to Oda and returns `{ authorizeUrl }`. It uses the same OAuth client, authorize URL builder, PKCE and redirect URI (`<WebOrigin>/oda/callback`) as T-053; no second client is registered.
4. **Sign in at Oda**, back to the same callback page `/oda/callback`. The page tells the two actions apart by its pending record (`kind: "sync"` or the existing cart week record, both only in `sessionStorage`, both cleared when read, ten-minute TTL; the sync record holds no names or ids).
5. **Review request.** The callback page calls `POST /api/households/{h}/oda-sync/review` `{ state, code }` (or `{ state, error }` when the user cancelled). In this one request the server exchanges the code, searches, reads `likely_to_buy` once, revokes the token, and returns the review list. The page never calls `review` twice (same one-run-per-page-load rule as the cart callback; a reload shows "start again").
6. **Review screen** (below), the user ticks rows and taps "Save choices". The screen calls the bulk `PUT /oda-preferences` with the ticked ids only. No Oda connection exists any more at that time, so saving needs none.

### Which ingredients
The set is computed on the server at `start` (to refuse an empty run and show the count) and again at `review` from the same options (carried in the flow cookie, so they cannot be changed in between):
- Distinct `IngredientId`s of the household's recipe ingredient lines (`RecipeIngredients`, tenant-filtered; the primary ingredient of a line only, not `RecipeIngredientAlternative` rows). Free-text import artifacts are not ingredients and are not searched (rule 5).
- Staples (`Ingredient.IsStaple`) are excluded unless `includeStaples`.
- Ingredients that already have a `PreferredOdaProduct` row are excluded unless `includeExisting`.
- Order: number of recipes using the ingredient (descending), then name in the request language, then id (stable, so `offset` is meaningful). The run takes `Oda:MaxSyncIngredients` (default 200, Q-039) starting at `offset`; the response says how many were not checked.
- The query is the ingredient's name in the request language (`Accept-Language`, as the shopping list does). Nothing else is sent to Oda: no household id, user, recipe or quantity.
- Empty set: `start` returns 409 `urn:foodplanner:problem:oda-sync-nothing-to-sync` (no recipes, all ingredients staples or already chosen); the client explains which and offers the checkboxes. `start` returns `{ authorizeUrl, ingredientCount, notCheckedCount }` so the confirmation can say "120 ingredients" (a count only).

### Oda calls and call budget
- Per run: `ceil(n / 10)` `product_search` calls (at most 10 queries each, `size` = `Oda:SearchPageSize`, default 10, page 1 only) plus at most 1 `likely_to_buy`. 150 ingredients is 15 searches + 1; the default cap of 200 is at most 20 + 1. Besides tool calls: discovery, token exchange, `tools/list` and the revoke, as in T-053.
- Searches run one after the other, never in parallel, and each batch is sent once (no retry). `likely_to_buy` is read after the last search and only when at least one ingredient has an available hit (T-114 rule, same fallback). Not used: `manipulate_cart`, `get_cart`, `clear_cart`, `get_orders`, `get_order`, recommendations, product-by-id lookups, paging.
- The connection check for this action requires only `product_search` (and uses `likely_to_buy` when offered); the cart tools are not required. The MCP session factory takes the required tools as a parameter; the T-053 cart action keeps requiring all three. A missing tool or argument fails closed (`oda-unavailable`).
- Time and limits (Q-039): a total budget `Oda:SyncBudgetSeconds` (default 90) is checked before each call. When it is spent, or Oda answers 429, a 4xx/5xx or a changed shape after at least one batch succeeded, the run stops without retrying and returns the rows found so far with `stopped` set (`time` | `oda-limit` | `oda-error`) and the remaining ingredients counted in `notCheckedCount`; the screen then offers "Check the next ones" (a new run with `offset`). A failure before any batch succeeded (exchange refused, tools missing, first search fails, token no longer accepted) is 502 `urn:foodplanner:problem:oda-unavailable` with `connectionClosed` and `connectionMessage` (T-053 wording), no rows, no upstream body. Each call keeps the per-call timeout `Oda:TimeoutSeconds` (30). A 429 or limit response is never retried or worked around.
- Revoke: in the `finally` path as T-053 (success, partial, error, cancellation of the request): revoke at `/o/revoke_token/`, retried once; `connectionClosed: false` plus the Privacy & security message if it still fails. The review is returned only after the revoke finished. The token and code live only in the memory of this request (T-053 token handling applies unchanged: redacted type, never persisted, logged or sent to the browser).

### Matching and the review list (pure, `Domain`)
Input per ingredient: its name, its available/unavailable search hits in rank order (page of 10), its existing preferred id if any (only present with `includeExisting`), and the set of usually-bought ids. Rules (the T-114 matcher is reused, not duplicated):
1. Candidates are hits with `availability.isAvailable = true`.
2. **usually-bought**: the best-ranked candidate whose id is in the usual set (a usual product that this ingredient's own search did not return is never offered). Row is pre-ticked.
3. **suggestion**: otherwise the first candidate. Row is unticked.
4. **not-found**: no hits (`reason: no-match`) or no available hit (`reason: unavailable`). Left alone: no checkbox, nothing saved.
5. Ingredients with an existing choice (`includeExisting`): if the existing id is among the candidates the row is `current` (category `current`, unticked, no change proposed unless the user picks another option), otherwise the row is classified by rules 2 to 4 as an unticked `replaces` row (the old choice is not usable now). Existing choices are never pre-ticked.
6. Alternatives: up to 4 more available hits in rank order, so a row has at most 5 options; the suggested or usual product is always among them; the current choice is included when among the candidates. Ids are exact integers, no name matching.

### Review response
`POST review` 200:
`{ status: "done" | "partial" | "cancelled", stopped: null | "time" | "oda-limit" | "oda-error", usuallyBought: "used" | "unavailable" | "skipped", rows: [...], notCheckedCount, connectionClosed, connectionMessage }`.
Each row: `{ ingredientId, ingredientName, category: "usually-bought" | "suggestion" | "current" | "not-found", reason: null | "no-match" | "unavailable", hasExistingChoice, selectedProductId: long | null, preticked: bool, options: [{ productId, productName, isUsual, isCurrent }] }`. `selectedProductId` is the usual or suggested product (null for `current` and `not-found`). Rows are ordered by category (usually-bought, suggestion, current, not-found), then by the run order. Product names and ids exist only in this response and in the page's React state: not stored, not cached, not written to browser storage, not logged. `error` in the request gives 200 `{ status: "cancelled", rows: [] ... }` with no call to Oda. A cookie that is missing, expired, reused, tampered, of another user, household or kind gives 400 `oda-state-invalid`, identical in every case, no call to Oda.

### Flow state (extends T-053 and Q-033)
The same encrypted `__Host-foodplanner-oda-flow` cookie (10 minutes, single use, Data Protection) is used; `OdaFlowState` gains `Kind` (`cart` default | `sync`) and, for `sync`, `IncludeStaples`, `IncludeExisting`, `Offset`; the week is unused for `sync`. `Take` refuses a cookie of the other kind with the same `oda-state-invalid`, so a cart cookie cannot complete a sync and the reverse. No table, no migration. Starting either action replaces the cookie of the other.

### Bulk save
`PUT /api/households/{h}/oda-preferences` with `{ "items": [ { "ingredientId": "...", "odaProductId": 123, "replace": false } ] }` (upsert of the listed items, all other rows untouched; the single-item `PUT /{ingredientId}` of T-052 is unchanged). Unsafe method, antiforgery group.
- At most `Oda:MaxBulkPreferences` items per call (default 200); empty, over the limit, a duplicate `ingredientId`, or any `odaProductId` missing, not whole or <= 0: 400 ValidationProblem naming the field (`items`, `items[i].odaProductId`).
- Never overwrite unless ticked: an item for an ingredient that already has a row is applied only when `replace: true` (the client sends `true` only for rows the user ticked that had an existing choice); otherwise it is skipped and reported. New rows are created regardless of `replace`.
- The T-052 cap of 500 rows per household counts the rows after the call; exceeding it is 409 `oda-preference-limit` and nothing is saved. The whole call is one tracked `SaveChanges` (all or nothing); a lost unique-index race is retried once, then 409 `oda-preference-conflict`. An unknown or foreign ingredient id anywhere in the list: 404 `ingredient-not-found`, nothing saved.
- Response 200 `{ created, replaced, unchanged, skippedExisting: [ingredientId] }` (counts and ids only). Nothing calls Oda; no product name is accepted or stored; `ICurrentUser` is not recorded.
- Rows with identical id to the stored one are `unchanged` (no write).

### Review screen (web, lazy route; 390px, nb + en)
- Route `/shopping/oda-sync` is not reached by link directly; the callback page renders the review in place (same route `/oda/callback`, code-split component `OdaSyncReview`, loaded only after the callback sees a `sync` pending record). The entry button and confirmation live in the existing `oda-choices` route chunk. The generated TS client is used; no hand-written API client.
- Layout (390px, one column): heading and one summary line ("12 you usually buy, 30 suggestions, 4 not found"), an alert only when `connectionClosed` is false (Privacy & security step), a note when `stopped` or `notCheckedCount` > 0 with "Check the next ones" (starts a new run with `offset` = previous offset + ingredients searched in this run - choices newly created by the save, because saved choices drop out of the next list; with "also check ingredients that already have a choice" on, nothing is subtracted. Decided at verification 2026-11-24), then three sections with a "Tick all" / "Untick all" button each for usually-bought and suggestions. Each row is a full-width label with a checkbox (the whole row is the touch target, min height 44px), the ingredient name, and the selected product name, wrapping, nothing clips or scrolls sideways. A row with more than one option has "Choose another" (44px) that opens an inline radio list (each option min 44px; tapping a different option selects it and ticks the row). `not-found` rows are plain text with the reason and no control. A sticky bottom "Save choices (n)" button (44px, disabled at 0) with a count of ticked rows.
- Pre-ticked rows are usually-bought only. A suggestion or `replaces` row is never ticked until the user does it. After saving: "Saved n choices" with how many existing ones were kept, and a link back to "Your Oda choices".
- The review is held in React state only; leaving or reloading the page loses it (the screen says so once: "Save before you leave; the list is not kept"). Nothing from Oda is written to `localStorage`/`sessionStorage`. Product names are escaped text.
- Errors from `review` (502, 400 state invalid, 429 rate limit, network): a plain message with "Try again" (starts again from the confirmation); the 502 message mentions no Oda internals. Errors from the bulk save keep the list and ticks and show the ProblemDetails message inline (409 limit, 404, 429, network).
- Strings in nb and en, both present (an i18n completeness test as for other screens).

### Nothing else is stored or logged
- Stored: only `PreferredOdaProducts` rows (T-052 columns) for ticked items. No sync history, "last synced", result, name, price, brand, URL, hit list or usual set; no new table or migration (`Migration: no`).
- Log: one line per review, as T-053: household id, user id, counts (ingredients searched, usually-bought rows, suggestions, not-found), `stopped` word, whether history was read, whether the connection was closed, duration. No product id, product name, ingredient name, token, code, verifier or `state`. One line per bulk save with counts only.
- Rate limit: `start` and `review` use the `oda-action` policy per user (T-053; 429 `rate-limited` with `Retry-After`).

### Architecture
- `Domain` (pure, thorough unit tests): ingredient selection ordering and paging, query batching (10 per call), the classifier above, bulk-save planning (create / replace / unchanged / skipped). No Oda, EF or ASP.NET types.
- `Infrastructure/Oda`: a new `OdaSyncAction` beside `OdaCartAction` sharing `OdaOAuth` and the session; `ICartProviderSession` is reused for `SearchAsync` and `ReadUsuallyBoughtIdsAsync` or a smaller search-only port is extracted, whichever keeps the cart action unchanged. The architecture test that forbids static product collections and the one that forbids Oda types in `Domain` cover the new code.
- Api: `MapOdaSyncEndpoints` (`start`, `review`) and the bulk `PUT` in `MapOdaPreferenceEndpoints`; OpenAPI contains all three; TS client regenerated.
- Options added to `OdaOptions`: `MaxSyncIngredients` (200), `SyncBudgetSeconds` (90), `MaxBulkPreferences` (200); `docs/domain.md` "Oda cart, session-only" documents them.

## Out of scope
Adding anything to the Oda cart or any ordering; order history (`get_orders`, `get_order`) and recommendations; storing names, prices or the review; scheduled or automatic syncing; syncing items of one week's list (that is the cart fill of T-053); pack-size or quantity logic; per-member choices; a standing Oda connection; searching by typed name; changing T-052's single-item endpoints or the T-114 matching; the help page and "Kom i gang" card themselves (T-131; this task only adds its own how-to entry); push notification or realtime sync; the privacy page wording (T-117, existing T-052 sentence covers the stored id).

- [ ] `Sync_other_household_forbidden`: an Adult of A calling the three endpoints under household B gets 403; B's recipes, ingredients and choices are not read.

# Spec: EF Core base and tenancy infrastructure (T-008)
## Goal
Every later feature gets a database context where household-owned rows are isolated automatically. Reads only ever see the current household's rows, and writes that would cross or lack a household fail before reaching SQL.

## Users & roles
This task has no endpoints and no roles. Roles (Owner, Adult, Child) are added by T-011 and enforced by its policies, not by the data layer. The data layer enforces only tenancy: which household a row belongs to. This holds whatever the caller's role.

## Behaviour
**Contracts owned here:**
- `Foodplanner.Domain.Tenancy.ITenantEntity` with `Guid HouseholdId { get; }`. Domain types expose no public setter. Infrastructure assigns the value through the EF change tracker.
- `Foodplanner.Domain.Tenancy.ICurrentHousehold` with `Guid? HouseholdId { get; }`. `null` means "no household context". T-011 adds `HouseholdRole? Role` and provides the real implementation. No other spec redefines this interface.
- `Foodplanner.Domain.Common.Entity`: abstract base with `Guid Id`. Keys are generated by EF Core as sequential GUIDs.
- `Foodplanner.Infrastructure.Persistence.AppDbContext`, the single application context. T-009 changes its base class for Identity; it stays one context.
- `TenancyViolationException` (Infrastructure).
- The Testcontainers SQL Server fixture in `Api.Tests`.

**Contracts used from elsewhere:** the layout and build rules from T-002.

Rules:
- **Read filter.** At model build, every entity type implementing `ITenantEntity` gets a global query filter `HouseholdId == <context's current household>`, applied by convention. Feature code never adds the filter by hand. The filter reads the household from a property on the `AppDbContext` instance, not from a captured value, because the EF model is cached across requests. With no household context (`null`), filtered queries return no rows. The filter also applies to `ExecuteUpdate` and `ExecuteDelete`.
- **Write guard.** A `SaveChanges` interceptor checks every tracked `ITenantEntity` before any SQL is sent:
  - **Added:** with no household context, throw `TenancyViolationException`. If `HouseholdId` is empty, set it to the current household. If it is set to a different household, throw.
  - **Modified or Deleted:** if `HouseholdId` differs from the current household, throw. If `HouseholdId` itself was modified, throw.
- **Audit timestamps.** `Entity` types get shadow properties `CreatedAt` and `UpdatedAt` (`datetimeoffset`, UTC). The interceptor sets them from `TimeProvider`.
- **Filter bypass.** Nothing in this task calls `IgnoreQueryFilters`. Any sanctioned bypass is decided by Q-006.
- **Placeholder household context.** Until T-011 lands, the Api registers a placeholder `ICurrentHousehold` that always returns `null`.
- **Migrations.** They live in `src/Infrastructure/Persistence/Migrations`. The first migration, `Initial`, creates only the baseline schema. The app never calls `Migrate()` or `EnsureCreated()` at startup. Tests apply migrations explicitly.
- **Test fixture.** One SQL Server Testcontainer per test assembly (xUnit assembly fixture). Each test class gets a fresh, uniquely named database with migrations applied. Tenancy behaviour is tested with a test-only `AppDbContext` subclass that adds a test entity `TestNote : Entity, ITenantEntity`. That entity never enters the production model or migrations. Docker is required to run `verify.sh` from this task on.
- **Errors.** A `TenancyViolationException` is a programming error, so it surfaces as 500. T-013 renders it as ProblemDetails.

## Out of scope
Real entities (Household, Membership, Identity tables: T-009 and T-011), the `ICurrentHousehold` implementation and roles (T-011), the reusable isolation harness and its reflection coverage check (T-012), global catalog rows with `HouseholdId = null` (T-020 extends the filter), soft delete, concurrency tokens, and migration bundles in CI/CD (T-005, T-007).

## Acceptance criteria (each must be testable)
- [ ] `Filter_returns_only_current_household_rows`: with rows for households A and B and the context set to A, `Set<TestNote>().ToListAsync()` returns only A's rows. With the context set to B, it returns only B's rows.
- [ ] `Filter_is_not_cached_across_contexts`: two contexts created in the same test with A and B as their household each see only their own rows. This catches a captured filter value.
- [ ] `Filter_returns_nothing_without_household_context`: with a `null` context, the query returns 0 rows.
- [ ] `Find_by_id_of_other_household_returns_null`: `FindAsync` or `FirstOrDefaultAsync` by id for B's row with the context set to A returns `null`.
- [ ] `ExecuteDelete_does_not_touch_other_household`: `ExecuteDeleteAsync()` on all `TestNote`s with the context set to A leaves B's rows in the database. The test checks with a raw SQL count.
- [ ] `Add_without_household_context_throws`: `SaveChangesAsync` throws `TenancyViolationException`, and no row is inserted.
- [ ] `Add_sets_household_from_context`: an added entity with an empty `HouseholdId` is saved with the current household id.
- [ ] `Add_for_other_household_throws`, `Update_of_other_household_row_throws`, `Delete_of_other_household_row_throws` and `Changing_HouseholdId_throws` each throw `TenancyViolationException`, and the database is unchanged. The update and delete cases use an attached entity that carries B's `HouseholdId` while the context is A.
- [ ] `CreatedAt_UpdatedAt_set_from_TimeProvider`: with a fake `TimeProvider`, insert sets both timestamps and a later update changes only `UpdatedAt`.
- [ ] `Migrations_apply_to_empty_database`: `MigrateAsync()` on a fresh Testcontainers database succeeds and `__EFMigrationsHistory` lists `Initial`.
- [ ] `No_pending_model_changes`: `Database.HasPendingModelChanges()` is `false` for the production `AppDbContext`.
- [ ] `Api_startup_does_not_migrate`: starting the Api against an empty database leaves no `__EFMigrationsHistory` table.

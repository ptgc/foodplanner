# Domain

## Glossary
- **Household**: tenant. Owns all data except global catalog data.
- **User**: login identity (external provider or local). **Membership**: User in a Household with a role.
- **Member profile**: a person in a household; kid profiles have no credentials and are selected on a logged-in device.
- **Staple**: ingredient flagged `IsStaple` (salt, oil, flour). Never auto-added to the list; shown in a "check you have these" section.
- **Pantry item**: household memory of confirmed staples (optional expiry); confirmed, unexpired staples are not prompted in the shopping list again (see Pantry memory).

## Roles (per membership)
Owner: manage members, delete household. Adult: edit recipes/plans, order. Child: pick meals, check off items; no recipe edits, no orders.

## Core entities
Household, User, Membership, MemberProfile, Recipe, RecipeStep, RecipeIngredient(amountKind, quantity, unit, ingredientId, purpose, isOptional, note; alternatives, T-076), Ingredient(IsStaple, Dimension; global or household), Unit(global; dimension + factor to base), Tag/Category, MealPlan, MealPlanEntry(date, recipe, servings, pickedBy), ShoppingList, ShoppingListItem(ingredient, mergedQuantity, unit, checked, sources), PantryItem, RecipeImport(import artifact: original text + editable draft), IngredientProductMapping(household, ingredient -> provider SKU).

## Tenancy
Shared DB/schema. `HouseholdId` on every household-owned row. Global catalog rows (ingredients, seed recipes) have `HouseholdId = null`, read-only to households; households may create their own. Enforced by EF global query filter + isolation tests.

How it is enforced (T-008, `src/Infrastructure/Persistence/Tenancy`):
- Read filter: named query filter `Tenant` on every `ITenantEntity`, from `ICurrentHousehold`; no household context means no rows. It also applies to `ExecuteUpdate`/`ExecuteDelete`.
- Write guard: a SaveChanges interceptor rejects Added/Modified/Deleted tenant rows without or outside the current household, and any change of `HouseholdId`, with `TenancyViolationException` (a 500).
- `HouseholdId` is a concurrency token: UPDATE/DELETE also match the stored `HouseholdId`, so a forged detached entity (own household, other household's row id) fails with `DbUpdateConcurrencyException`. T-013 must map that deliberately.
- `ITenantWriteScope` (only `ITenantResolution`, T-011) covers Added and Modified only. Delete inside a scope throws by design, so invites are marked used, not deleted.
- Household context (T-011, Q-004): every household-scoped endpoint lives under `/api/households/{householdId}/...` (`MapHouseholdScopedGroup`). `HouseholdContextMiddleware` (after authentication, before authorization, because policies run before endpoint filters) resolves the caller's membership once per request into `ICurrentHousehold` (`HouseholdId` and `Role`, both `null` for a non-member). Policies `HouseholdMember`/`HouseholdAdult`/`HouseholdOwner` are hierarchical and are the only readers of `Role`. "Active household" is a client choice; the server holds none.
- `Household` is the tenant root (no `HouseholdId`, not filtered). `Membership` and `Invite` are tenant entities. `ITenantResolution` (`Foodplanner.Infrastructure.Persistence.Tenancy`) is the only code that calls `IgnoreQueryFilters` or opens a write scope. Invites are marked accepted, never deleted; only the SHA-256 token hash is stored.
- Identity tables (`AspNetUsers`, claims, logins, tokens; T-009) are global identity data, not tenant entities: no `HouseholdId`, no filter. A User belongs to households only through Membership (T-011). The role tables are not created because roles are per membership.
- Isolation suite and architecture rules (T-012). Adding an `ITenantEntity` means adding one `TenantIsolationCase.For<T>(...)` line to `tests/Api.Tests/TenantIsolation/TenantIsolationRegistry.cs`; `TenantIsolationCoverageTests` fails, naming the entity, if it is missing. The harness then proves for it, against SQL Server: reads (list, Find, AsNoTracking, projection, Include) never see another household's row; insert for another household, update, delete and any `HouseholdId` change fail (`TenancyViolationException`, or `DbUpdateConcurrencyException` for a forged detached entity) and the other row is unchanged by raw SQL; `ExecuteUpdate`/`ExecuteDelete` touch only the current household. `Household` and the global identity tables are on `TenantCoverage.Exempt`, each with a reason; any other entity that is not an `ITenantEntity` fails the coverage test until it is exempted or made a tenant entity. `Architecture.Tests` enforce: `IgnoreQueryFilters` and `ITenantWriteScope.ForHousehold` only in `TenantResolution.cs` plus the documented test-support allow-list in `TenantSourceRules.Allowed` (solution-wide, src and tests; unnamed `IgnoreQueryFilters()` is never allowed); no `SetProperty` of `HouseholdId` in src; no raw SQL or raw ADO.NET in src outside Migrations; model rules (no owned `Entity`/`ITenantEntity` type, every `Entity` has `CreatedAt`/`UpdatedAt`, every tenant entity has the `Tenant` filter and the concurrency token, and a `HouseholdId` property on a type that is neither `ITenantEntity` nor `ICatalogEntity` fails); no `AllowAnonymous`, and always a policy, under `/api/households/{householdId}` (`HouseholdRouteRulesTests`); `GetMembershipsForUser` is called only from `ListHouseholds`.
- Account creation (T-072, Q-011). Register records only the email; the emailed link opens `/set-password`, where the person chooses the password, and only then the account has a password and is confirmed. An attacker who registers someone else's address therefore never knows or sets the password. Accounts without a password cannot sign in. The link carries a one-time token, so the web app moves it out of the URL into history state on arrival and sends `Referrer-Policy: no-referrer` (nginx, Vite dev server) plus a `referrer` meta tag on that route.
  - Re-registering an unconfirmed address sends a fresh link and invalidates earlier ones, at most once per `Auth:ResendCooldownMinutes` (default 5) per address; inside the cooldown the answer is the same 202 and nothing happens. This bounds link-killing and inbox flooding.
  - Unconfirmed accounts are removed after `Auth:ConfirmationTokenLifetimeHours` (default 24) by the `UnconfirmedAccountCleanup` hosted service, so a squatted address frees up. The age is `AspNetUsers.RegisteredAt` (T-074, Q-016; replaces the T-072 claim `foodplanner:registered-at`), served by a filtered index on unconfirmed users. It is set on register, refreshed together with the security stamp in one save by every link that is sent (kept deliberately: the owner can always register again, so keeping an account alive gives a squatter nothing), and set to null on confirmation; confirmed and seeded users have null. An unconfirmed account with null (from before T-072) gets its window started by the first cleanup pass. The migration backfilled the column from existing claims and deleted them. Races between register, confirm and cleanup are settled by the Identity concurrency stamp on the user row.
  - Known small leaks: the first `GET /set-password?userId=..&token=..` still lands in nginx or ingress access logs (the token is single use and expires after 24 hours); and register answers a new or unconfirmed address slightly slower than a confirmed one because the mail is sent inside the request. T-017 should send mail off-request (queue or background send) to remove that timing signal.
  - The cleanup assumes unconfirmed users have no memberships or invites (the Memberships FK cascades, Invites are RESTRICT). T-010 (external login) and the invite flows must not create unconfirmed users that hold memberships or invites.
- Rule for foreign keys between tenant entities (T-021 and later). The filter and the write guard protect a row's own `HouseholdId`, not the ids it points to: a tenant row, or a many-to-many join row, can be saved pointing at another household's row, because the database only checks that the target exists. Resolve every id taken from a client through the filtered set first (B's row is then not found: answer 404) and never write the id otherwise. Feature tests post another household's id, expect the 404, and call `CrossHouseholdLinks.AssertNoneAsync` (`tests/Api.Tests/TenantIsolation`), which walks the EF model and looks in SQL for any link that crosses households. `TenancyKnownGapTests` and `CrossHouseholdLinksTests` pin the unprotected paths so nobody assumes otherwise. The Api test database fixtures (`AuthDatabase`, `TenancyDatabase`) run the same check over the whole database on teardown, so a cross-household link created by any test fails the run. Many-to-many between tenant entities must use an explicit join entity that implements `ITenantEntity` (and gets its own isolation case); the model rules reject an implicit (shared-type) join entity, or any non-tenant entity, that points at two tenant entities. Production-side composite foreign keys `(HouseholdId, Id)` were not chosen (Q-012 option 2).
- Save-time reference check (T-073, Q-012 option 3). The save interceptor (`TenancyReferenceCheck`, called from `TenancySaveChangesInterceptor`) refuses, with `TenancyViolationException` (a 500, before any SQL), an Added or Modified `ITenantEntity`/`ICatalogEntity` whose new or changed foreign key points at another household's row. It is derived from the EF model (every foreign key whose principal is a tenant or catalog entity, so new entities and keys are covered automatically): the referenced row must be global (household null, catalog principals only) or owned by the saving row's household. Handlers keep resolving ids through the filtered sets and answering 400/404 first; this is the backstop. Cost, bounded: at most one read per distinct principal type per `SaveChanges` (`WHERE key IN (...)`, key and owner only, untracked, batched over all rows), none when no such key is new or changed; principals added in the same save are not read; a principal that does not exist is left to the database foreign key; only single-column Guid foreign keys are supported (anything else throws `InvalidOperationException` at save, so it cannot pass unchecked). The read bypasses the tenant filter by name, so it lives in `TenantResolution.cs` (`ReferenceOwnerLookup`), the one file the bypass rule allows. Not covered: implicit (shared-type) many-to-many joins (forbidden between tenant entities by the model rules), `ExecuteUpdate`/`ExecuteDelete` and raw SQL (forbidden in src). `CrossHouseholdLinks` is now a backstop and test helper: it finds links planted by other means. Tests: `SaveTimeReferenceCheckTests` (one theory row per tenant or catalog foreign key of the production model: other household refused when added and when changed, own and global rows save; query count asserted with a command interceptor) and `SaveTimeReferenceCheckCatalogModelTests` (catalog row pointing at household data).
- Global-or-household catalog entities (T-020, `HouseholdId` null per ADR 0005). `ICatalogEntity` (`Foodplanner.Domain.Catalog`, `Guid? HouseholdId`) is deliberately not `ITenantEntity` (which promises a non-null owner). `Ingredient` is one. The same conventions apply, with differences: the query filter keeps the name `Tenant` (one name, so the bypass rules and model rules cover both) but is `HouseholdId == null || HouseholdId == current`, so global rows are visible to every household and, with no household context, only global rows are; `HouseholdId` is a nullable concurrency token. The save guard adds: an Added catalog row with a null household is refused (`TenancyViolationException`), so request code cannot create a global row (a new row starts with its household or `Guid.Empty`, which is stamped like a tenant row; another household's id is refused); an Update or Delete of a row whose stored household is null (a global row) is refused; any change of `HouseholdId`, including to or from null, is refused. Global rows are written only by the seed: `CatalogSeedData` (`HasData`, fixed UUIDv5 ids from a stable key, so a replay conflicts instead of duplicating) applied by migration `AddCatalog` in every environment through `local-migrate`; the seed never passes through SaveChanges. The data lives in `Domain/Catalog/IngredientSeed.cs` and `UnitSeed.cs` (one file each; names are Norwegian bokmål, Q-013 open). `Unit` is global only (no `HouseholdId`, on `TenantCoverage.Exempt`): dimension Mass/Volume/Count and a factor to the base unit g/ml/stk; ts/ss/kopp are volumes (5/15/250 ml), fedd/klype/stk are Count units that do not convert to each other (`UnitConversion`); merging is T-031. Ingredient names are unique per household and among the global rows (unique index on `(HouseholdId, Name)` with no filter), compared case-insensitively by the database collation; the create endpoint also refuses a household name that equals a visible global one (409), since the index cannot span the two.
- Harness for catalog entities. Register with `TenantIsolationCase.ForCatalog<T>(...)`; `TenantIsolationCoverageTests` fails if an `ICatalogEntity` is missing, is registered with `For`, or is on `Exempt`. It runs every tenant check on the household rows (global rows are allowed in the results), plus `GlobalRowsAreVisibleToEveryoneAsync` and `GlobalRowsAreReadOnlyAsync` (a household cannot create a null-household row, nor update, delete, claim or release a global row: detached, `DbSet.Update`, forged and tracked variants; the global row is unchanged by raw SQL). The harness makes a row global with raw SQL (`MakeGlobalAsync`) to stand in for a seeded row. Known gap, pinned by `BulkOperationsReachGlobalRowsAsync`: `ExecuteUpdate`/`ExecuteDelete` skip the guard and the catalog filter admits global rows, so a household can reach them; `TenantSourceRules.BulkWrites` therefore forbids both in src except `TenantResolution.cs`. Stamping in the harness goes through the EF entry (backing field), so a get-only `HouseholdId` works. `CrossHouseholdLinks` includes catalog entities as principals and dependents: a NULL principal is never a violation, a global row pointing at household data is. The model rules accept a `HouseholdId` on an `ICatalogEntity` only with the "global or mine" filter and a nullable concurrency token, and reject a type that is both `ITenantEntity` and `ICatalogEntity`.
- Recipes (T-021, migration `AddRecipes`). `Recipe`, `RecipeStep` and `RecipeIngredient` are three `ITenantEntity` tables with their own Guid key (no owned collections: the model rules reject an owned `Entity`, and the harness needs a single Guid key); children point to the recipe by `RecipeId` with no navigations (a required navigation to a filtered entity raises EF warning 10622) and are ordered by a 0-based `Position`. A line has `IngredientId` (global or own ingredient), `Quantity` (decimal(18,4), greater than 0, at most 100000, at most 4 decimals) and `UnitId`; "to taste" was quantity and unit both null (since T-076 it is the explicit amount kind `ToTaste`; see "Ingredient amount kind, purpose, optional and alternatives"). Cascades: Household -> Recipe -> steps and lines is the only cascade; the children's own Household FK and the Ingredient and Unit FKs are NO ACTION (SQL Server rejects two cascade paths, and a line must not vanish with an ingredient); deleting a household still removes everything, as `MigrationTests.AddRecipes_migration_applies_and_deleting_a_household_removes_its_recipes_and_ingredients` shows. Endpoints under `/api/households/{id}/recipes` (member read, adult write). Following the Q-012 rule, every ingredient and unit id in a body is resolved through the filtered sets before saving and an unknown or other household's id is answered `400` ValidationProblem on `ingredients[i].ingredientId` or `.unitId` (the response is the same for "does not exist" and "belongs to someone else", so ids do not leak; the 404 above stays for ids in the route, e.g. another household's recipe id, which is `404 recipe-not-found`). PUT replaces steps and lines by tracked deletes and inserts in one save; a `DbUpdateConcurrencyException` (concurrent delete, or the forged update of T-008) is answered `409 recipe-conflict`.
- Tags, categories and recipe filtering (T-023, migration `AddTags`). `Tag` (`Domain/Recipes`) is a global-or-household `ICatalogEntity` (T-020 pattern, registered with `ForCatalog`) with a `Kind` (`Category`: what kind of meal; `Tag`: a property of the recipe) and a name (at most 50 characters, unique per household and among the global rows, case-insensitive; a household name equal to a visible one is `409 tag-exists`). The global set is seeded as migration data from one file, `Domain/Recipes/TagSeed.cs` (Norwegian bokmål, Q-013 open, so only the Name column changes; fixed UUIDv5 ids from the key): categories Middag, Lunsj, Frokost, Dessert, Bakst; tags Vegetar, Fisk, Kylling, Kjøtt, Pasta, Suppe, Rask (under 30 minutes, by convention only, it is not computed), Barnevennlig. Applying the migration twice is a no-op. Endpoints: `GET /api/households/{h}/tags` (global plus own, categories first then by name; any member) and `POST` (Adult or Owner); there is deliberately no PUT or DELETE route, and the save guard refuses writes to global rows anyway. `RecipeTag` is the explicit join (`ITenantEntity`, own Guid id, unique `(RecipeId, TagId)`, no navigations); cascade only Household -> Recipe -> RecipeTag, the RecipeTag FKs to Household and Tag are NO ACTION, so a tag in use is never deleted from under a recipe (and deleting a household still removes its tags and links in one statement). Recipe POST/PUT take `tagIds` (PUT replaces the set; absent means none; repeated ids are ignored; at most 20). Per the Q-012 rule each id is resolved through the filtered `Tags` set before saving: another household's or an unknown id is `400` ValidationProblem on `tagIds[i]` (the same answer for both). PUT diffs the links with tracked removes and adds (no `ExecuteUpdate`/`ExecuteDelete`). Recipe detail and list items return `tags` (id, name, kind, isGlobal).
- Recipe list filters (T-023), `GET /api/households/{h}/recipes`. All filters combine with AND. `search`: case-insensitive "contains" on the title. `tagIds` (repeat the parameter): the recipe has ALL of them (at most 10). `maxMinutes` (0 to 2880): prep plus cook at most n; a recipe with neither time set is NOT matched because its time is unknown. `ingredientId` (repeat): the recipe has a line for ALL of them (at most 10). An unknown or foreign tag/ingredient id in a filter just matches nothing (no error, nothing leaks); an empty id, a malformed value or an out-of-range number is `400` ValidationProblem. Paging is `limit` (1 to 100, default 20) and `offset` over the total order title, then id (ties on equal titles are broken by id, in the database's order); `total` counts all matches. Offset paging is stable for inserts that sort after the page being read; an insert that sorts before it shifts later pages by one (the usual offset trade-off; a keyset cursor can replace it if the app needs infinite scroll under heavy concurrent editing).
- Meal plans (T-030, migration `AddMealPlans`). `MealPlan` (`Domain/MealPlans`, `ITenantEntity`) is one household's plan for one ISO-8601 week, identified by `WeekStart`, the week's Monday (`date`; Norway uses ISO weeks); unique `(HouseholdId, WeekStart)`. `MealPlanEntry` (`ITenantEntity`, own Guid id, no navigations) has `MealPlanId`, `Date` (Monday to Sunday of the plan's week, enforced in the domain and at the boundary), `RecipeId`, `Servings` (1 to 50) and `PickedByUserId`. A day can have several entries, ordered by date then creation. No slot column: add one later if a day needs named meals. Cascade: Household -> MealPlan -> entries only; the entries' own Household, Recipe and `AspNetUsers` FKs are NO ACTION (`MigrationTests.AddMealPlans_...` shows deleting a household still removes the lot).
- Meal plan API (T-030), `/api/households/{h}/meal-plans/{weekStart}` where `weekStart` is `yyyy-MM-dd` and must be a Monday (anything else is `400` ValidationProblem on `weekStart`). `GET` never writes: with no plan yet it returns `{ id: null, weekStart, entries: [] }`; otherwise each entry has id, date, recipeId, recipeTitle, servings and `pickedBy` (userId, email). The plan row is created by the first `POST .../entries` (find-or-create; two members adding to a new week at once share one plan thanks to the unique index). `POST .../entries` takes `date`, `recipeId`, optional `servings` (default: the recipe's servings, capped at 50); the picker is always the caller (`ICurrentUser`), never the body. `PUT .../entries/{entryId}` changes `date` (same week) and `servings` only. `DELETE .../entries/{entryId}`. An entry is looked up under its own week (another week's route gives `404 meal-plan-entry-not-found`). Per the Q-012 rule the recipe id is resolved through the filtered `Recipes` set: another household's or an unknown recipe is `400` ValidationProblem on `recipeId` (same answer for both). A `DbUpdateConcurrencyException` is `409 meal-plan-entry-conflict`. Recipe thumbnails and cards come with T-022 and are not part of these responses yet.
- Meal plan authorization (T-030). Any member (Child included) reads and adds entries (`HouseholdMember`, the group default). Updating or deleting an entry uses the resource policy `MealPlanEntryOwnerOrAdult` (`src/Api/Authorization/MealPlanEntryAccess.cs`): the requirement succeeds for Adult or Owner, or for the member who picked the entry; so a Child changes only their own picks (`403 forbidden` otherwise). Endpoints ask through `IMealPlanEntryAccess` (which wraps `IAuthorizationService` with the entry as resource, so feature code never touches `ClaimsPrincipal`); the handler is policy code and the only place that reads the role. A non-member gets `403` from the group policy before any lookup.
- Recipe images (T-022, migration `AddRecipeImage`). `Recipe.ImageVersion` (`Guid?`) is the only database change: null means no image. Files live in Blob Storage (Azurite locally), container `recipe-images`, named `{householdId:N}/{recipeId:N}/{version:N}/{thumb|card|full}.webp`; every upload gets a new version and the previous version's blobs are deleted after the row points at the new one, so a stored file never changes (URLs are immutable) and a failed upload leaves the old picture. Sizes (`Domain/Images/RecipeImageSizes`): longest side 160 (thumb), 640 (card), 1600 (full), aspect ratio kept, never enlarged, lossy WebP quality 80. Served only through the API, never from storage: `GET /api/households/{h}/recipes/{r}/image/{version}/{size}` (member; looked up through the tenant filter, blob name built from the row's own ids, `Cache-Control: private, max-age=31536000, immutable`, `ETag`, 304). `PUT .../recipes/{r}/image` (Adult or Owner, multipart part `file`) and `DELETE .../image` (Adult or Owner). Recipe detail has `image { thumbUrl, cardUrl, fullUrl }` (null without an image); list items have `thumbUrl` and `cardUrl`. Upload rules: JPEG, PNG or WebP decided from the bytes (client content type and file name are ignored); at most 10 MB (`Images:MaxUploadBytes`, `413 image-too-large`); at most 8000 px on a side and 40 megapixels (`Images:MaxDimension`, `Images:MaxPixels`), checked from the header before pixels are decoded; animated files (APNG, multi-frame WebP; GIF has no loader at all) and corrupt or truncated files are `400` ValidationProblem on `file`. All metadata (EXIF incl. GPS, XMP, IPTC, ICC) is stripped; EXIF orientation is applied to the pixels and the picture is converted to sRGB. Processing is NetVips (libvips) in `Infrastructure/Images`. Deleting the recipe deletes its blobs; blob cleanup failures are logged and leave harmless orphans. A household delete does not remove blobs yet (no cleanup job).
- Deleting a recipe that is on a meal plan is refused: `409 recipe-in-use` (the entry FK to the recipe is NO ACTION; a race between the check and the delete is mapped to the same 409). Remove the entries first.
- The only `DbContext` in the production assemblies is `AppDbContext` (architecture test); a second context would bypass the filter, the guard and the coverage check.
- Not enforceable by a test, so a review item: a name for `HouseholdId` assembled at run time inside `SetProperty`; what `ListHouseholds` does with the roles it receives (the rule only limits who may call `GetMembershipsForUser`); an unrelated member named `ForHousehold` (the rule flags it, rename it). The source rules are lexical, so they can flag harmlessly: a factory called `ForHousehold`, `IgnoreQueryFilters` for a future non-tenant named filter (still only allowed in the resolution), or one of the raw-SQL names (`ToFunction`, `HasDbFunction`, `ToSqlQuery`, `CreateConnection`, ...) used legitimately; in `src` the names are also searched inside string literals. Add a reasoned entry to `TenantSourceRules.Allowed`, or rename. The harness limits are a single Guid key (`Entity.Id`) and exactly one row per household from the factory. The cached EF model holds the first context instance (and its `ICurrentHousehold`) as the filter's parameter template, so keep `ICurrentHousehold` implementations light.

## Quantities: conversion, merging, display and rounding (T-031, `Domain/Quantities`)
`Quantity` = decimal amount (null = "to taste") + `Unit`; never negative; decimal arithmetic only. `QuantityMerger` works on the quantities of ONE ingredient (the caller groups by ingredient).
- Merge (`Merge`, exact, no rounding, so it is associative, commutative and idempotent): Mass units add to one line, Volume units add to one line (ts/ss/kopp/dl are volumes); Mass and Volume are never merged (no density); Count units merge only with the same unit (stk+stk, fedd+fedd; stk and fedd stay separate lines); null amounts are never added, one to-taste line is kept per distinct unit. Output order: Mass, Volume, Count by code, to-taste by code.
- Display unit: Mass below 1000 g in g, from 1000 g in kg. Volume below 1000 ml in ml, from 1000 ml in l. dl, ts, ss and kopp are input units, never chosen. So 200 g + 0.3 kg = 500 g, 2 dl + 300 ml = 500 ml, 1 ss + 1 ts = 20 ml.
- Rounding (`ForDisplay`/`MergeForDisplay`/`Round`; half away from zero; a positive amount never rounds to 0, it shows one step): g 1, kg 0.1, ml 1, dl 0.1, l 0.1, ts 0.5, ss 0.5, kopp 0.25, stk 0.5, fedd 1, klype 1. Mass and Volume are rounded in g/ml first and the unit chosen after, so 999.6 g shows as 1 kg. Rounded results are for people only: never merge or scale them again.
- The display units come from a `UnitCatalog` (the caller passes the units loaded from the database; `UnitCatalog.Seed` for tests).

## Shopping list generation (T-032, `Domain/ShoppingLists`)
`ShoppingListGenerator.Generate(IEnumerable<PlannedMeal>, UnitCatalog)` is a pure function. `PlannedMeal` = recipe id, recipe servings, planned servings (both > 0) and `PlannedIngredient`s (ingredient id, name, IsStaple, `Quantity` for the recipe servings); T-033 maps plan entries and recipes onto these (see Shopping lists below).
- Scaling: each amount is multiplied by planned / recipe servings, exactly in decimal (multiply first, then divide), so 4 -> 3 servings is exactly 0.75. To-taste stays to-taste.
- Grouping and merging: by ingredient id, then `QuantityMerger.Merge` (exact). 200 g + 0.3 kg across two recipes = 500 g. Mass and volume of one ingredient stay separate lines.
- Rounding: once, at the end, via `ForDisplay`. Never round per recipe or before merging.
- Staples: an ingredient flagged staple in any entry goes only to the "check you have" section (no quantity), never to the main list, even when a recipe gives it an amount.
- Each item lists the distinct contributing recipe ids (ascending). Order of both sections: ingredient name (OrdinalIgnoreCase, then Ordinal, so æ ø å sort after z), then id; independent of input order.

## Shopping lists (T-033, migration `AddShoppingLists`)
The generator's result types are `GeneratedList`/`GeneratedItem`/`GeneratedStaple` (renamed from `ShoppingList` etc. so the stored entities can use the glossary names).
- Model (`Domain/ShoppingLists`, four `ITenantEntity` tables, own Guid keys, no navigations). `ShoppingList`: one per household and ISO week (`WeekStart` = the Monday, unique `(HouseholdId, WeekStart)`, same key as the meal plan). `ShoppingListItem`: `Section` (`Main` | `CheckYouHave`), `Checked`, `CheckedByUserId`, `CheckedAt`, `QuantityChangedSinceChecked`, `RowVersion` (rowversion), and EITHER `IngredientId` (generated; no free text) OR `Label` (manual, 1-100 chars; the only place free text exists, rule 5). `ShoppingListItemQuantity`: the structured display lines of an item (`Position`, `Amount` decimal(18,4) and `UnitId`; both null = "to taste"; a mass line and a volume line of one ingredient are two rows; a manual item has at most one; staples have none). `ShoppingListItemSource`: the contributing recipes of a generated item (unique `(item, recipe)`), for "from recipe X". A unique filtered index `(ShoppingListId, IngredientId) WHERE IngredientId IS NOT NULL` allows one generated item per ingredient. Cascade only Household -> List -> Item -> (Quantity, Source); the other FKs (Household on the children, Ingredient, Unit, Recipe, user) are NO ACTION. Deleting a recipe first removes its source rows (a stale list may still name it; recipes on a plan stay `409 recipe-in-use`).
- Endpoints under `/api/households/{h}/shopping-lists/{weekStart}` (`weekStart` a Monday `yyyy-MM-dd`, else `400` on `weekStart`). `GET` never writes: no list yet returns `{ id: null, weekStart, main: [], checkYouHave: [] }`; items carry name (ingredient name or label), `isManual`, `ingredientId`, `section`, `quantities` (amount + unit code), `recipes` (id + title), `checked`, `checkedByUserId`/`Email`/`At`, `quantityChangedSinceChecked`. `POST .../generate` (creates the list if missing, an empty plan gives an empty list), `POST .../items` (manual: `label`, optional `quantity` + `unitId` together; the unit is resolved before saving, unknown is `400` on `unitId`; at most 200 manual items per list), `DELETE .../items/{id}` (manual only), `PUT .../items/{id}/check` with `{ "checked": bool }`.
- Permissions: every member, Child included, may read, generate, add and remove manual items and check off (family use; the group default `HouseholdMember`, no role is read). A non-member gets `403`; another household's item id under your own household is `404 shopping-list-item-not-found`. Generated items cannot be removed (`409 shopping-list-item-generated`): change the plan and regenerate. Any member may remove any manual item.
- Generation: the plan entries of the week and their recipes are read through the filtered sets (own recipes, global plus own ingredients), mapped to `PlannedMeal`/`PlannedIngredient` (a "to taste" line has no unit in the recipe, so it gets the placeholder unit `stk` and is stored with no unit), and passed to `ShoppingListGenerator`. A read never regenerates: removing a plan entry changes the list only when someone regenerates.
- Reconciliation (`ShoppingListReconciler`, pure): generated items are keyed by `IngredientId` alone (an ingredient is in one section at a time). New ingredient: added. No longer in the plan: removed, checked or not. Still there: the item row, its checked state, checker and time are kept; quantities and sources are replaced when they differ. Manual items are never touched. Identical input changes nothing, so regenerating twice gives the same list (same ids, same JSON). If the ingredient switched section (its staple flag changed) the item moves and starts unchecked.
- Quantity-change rule: a CHECKED item whose quantities change on regeneration STAYS checked and gets `quantityChangedSinceChecked = true` ("you bought 500 g, now 700 g are needed"); an unchecked item is just updated. The flag survives further regenerations and is cleared by unchecking or by checking again (`PUT check true`, which keeps the first checker).
- Concurrency rule for check-off: `RowVersion` is an optimistic token on the item (besides the `HouseholdId` token), updates are tracked saves (no `ExecuteUpdate`). The request reads the item, applies set semantics in the domain (`SetChecked`), and saves; if the row changed in between (`DbUpdateConcurrencyException`) it re-reads and applies the same request to the fresh state, up to 5 times (then `409 shopping-list-conflict`). Consequences: the same value twice (two members checking one item) is not an error and the FIRST writer stays the checker (everyone sees the same checker); opposite values (check vs uncheck) end in the state of whichever request commits last, checker and time always coming from one writer, never a mix; a request that finds the item already in its wanted state writes nothing. A concurrent delete of the item is `404`. Concurrent regenerations are settled the same way (unique index plus retry; the loser re-reads and finds nothing left to change) and a list created by two members at once is one list.
- Notifier hook (`IShoppingListNotifier`, `Api/Features/ShoppingLists`): every saved mutation (generated, manual item added, item checked/unchecked, item removed) calls `NotifyAsync(ShoppingListChange(householdId, weekStart, kind, itemId))` after the save; implemented by `SignalRShoppingListNotifier` (T-034, see "Shopping list sync"; a failing notifier is logged, never undoes the change).
- Display order: items sort first by store section (T-085, see "Store sections"), then by name with a Norwegian (`nb-NO`) culture comparison in the API response (æ ø å come after z, in that order; the generator itself stays ordinal and culture independent); the runtime falls back to ordinal-ignore-case only when ICU is missing (invariant globalization).

## Shopping list export (T-050, ADR 0008)
- Port: `IShoppingListExporter` (`Domain/ShoppingLists/Export`, provider-neutral): `Name` (selector, e.g. `text`) and `ExportAsync(ShoppingListExport, ct)` returning `ShoppingListExportResult(Title, Text?, Url?)` (text for share/copy; a provider exporter such as Oda, T-053, may return a cart `Url`). The input `ShoppingListExport` is the list as a person sees it: week, locale, the two sections in display order, items with name in the request language (or the manual label), `IsManual`, `Checked` and display quantities (amount + unit code + unit name; null amount = to taste). No provider types in Domain (architecture test `ExporterBoundaryTests`). Implementations live in Infrastructure (`Infrastructure/Export`) and are registered with `AddShoppingListExporter<T>()`; `IShoppingListExporterSelector.Find(name)` picks one case-insensitively.
- Text exporter (`TextShoppingListExporter`, name `text`): headings per locale from a small table (nb: "Å handle" / "Sjekk at du har", en: "To buy" / "Check you have"; unknown locale = English), Markdown-style bullets `- Ris 500 g`, sections separated by a blank line, LF, no trailing whitespace or newline. "Check you have" staples are included as their own short reminder section; empty sections are omitted; checked items are never exported; to-taste and quantity-less manual items are the name alone; several lines of one item are joined by ", " (`- Olje 1 spiseskje, 2 dl`). Units: the code for g, kg, ml, dl, l, stk, otherwise the unit's name in the list's language. Numbers: decimal comma for nb, point for en. Order is the list's display order. A list with nothing left (or no list) exports one sentence ("Nothing to buy." / "Ingenting å handle."), never 404.
- Endpoint: `GET /api/households/{h}/shopping-lists/{weekStart}/export?format=text` (default `text`; any member; `Accept-Language` picks the language) returns JSON `{ format, title, text, url }` with `title` like "Shopping list, week 44" so the client can call `navigator.share({ title, text })` or copy `text`. Non-Monday `weekStart` or an unknown `format` is `400` (on `weekStart`/`format`), a non-member `403`.

## Pantry memory (T-037, migration `AddPantryItems`)
- Model: `PantryItem` (`Domain/ShoppingLists`, `ITenantEntity`, own Guid key, no navigations): `IngredientId`, `ConfirmedAt`, `ConfirmedByUserId`, optional `ExpiresAt`. Unique `(HouseholdId, IngredientId)`: confirming again updates the row (latest confirmation, user and expiry win). Cascade only Household -> PantryItem; Ingredient and user are NO ACTION. The ingredient may be global or the household's own: the endpoint resolves it through the filtered set (another household's id and unknown ids are both `400` on `ingredientId`), and the save-time reference check (T-073) is the backstop. Registered in the isolation harness (`TenantIsolationRegistry`).
- Staples only. The pantry applies to staples (`Ingredient.IsStaple`) and nothing else: confirming a non-staple is `400` on `ingredientId`, and the main list is never filtered. Reason: a non-staple is bought per recipe amount, so "I have it" has no lasting meaning.
- Generation: `PantryFilter.Apply(GeneratedList, IEnumerable<PantryEntry>, now)` (pure, `Domain/ShoppingLists`) runs after `ShoppingListGenerator.Generate` and removes staples with an active entry (no expiry, or `ExpiresAt` after `now`) from `CheckYouHave`. The API reads the household's pantry (filtered set), passes it with `TimeProvider.GetUtcNow()` and reconciles as before. Decision: confirmed staples are OMITTED from the stored "check you have" section, not shown collapsed; nothing disappears silently because `GET pantry` lists them and the shopping page shows "N staples you have at home" (expandable, each with "Not anymore").
- When it takes effect: on the next generate (regenerate) of a week. The endpoints do not edit existing lists; the web client calls generate right after a confirm or un-confirm (one tap = `PUT pantry` + `POST generate`), which also sends the `Generated` hub signal so other sessions refetch. No new change kind and no pantry event: a pantry change alone reaches no other session until someone regenerates; the page also re-reads `GET pantry` whenever a list state is accepted. Un-confirming brings the staple back on the next generate; expiry does the same (an expired entry stays stored, is not listed and no longer filters; the list already generated keeps showing what it showed until regenerated).
- Endpoints under `/api/households/{h}/pantry`: `GET` (active entries, by name in the request language: ingredientId, name, confirmedAt, confirmedByUserId, expiresAt), `PUT /{ingredientId}` with `{ expiresAt? }` (confirm "I have it"; `expiresAt` must be in the future, else `400` on `expiresAt`; `200` also for a re-confirm; a lost race is retried once, then `409 pantry-conflict`), `DELETE /{ingredientId}` (`204`, idempotent). Permissions: every member, Child included, may read, confirm and un-confirm (family use, like check-off; the group default `HouseholdMember`, no role is read); a non-member gets `403`.
- Web: each generated item in "Check you have these" has an "I have it" button (44px+, translated, disabled offline). The pantry summary sits above the add form.

## Shopping list sync (T-034, SignalR; client contract for T-036)
- Hub `ShoppingListHub` at **`/api/hubs/shopping-list`** (in-process SignalR; Azure SignalR Service is a later scale-out step, ADR 0007). Auth is the same `__Host-foodplanner` cookie as the REST API (same origin, nginx/Vite proxy `/api`, WebSockets enabled for `/api/hubs/`); no token in the URL. An anonymous negotiate or handshake is `401`. JSON protocol, camelCase, enums as strings.
- Methods (every one re-checks membership; the household id is the client's claim, never trusted): `JoinHousehold(householdId)` adds the connection to group `household:{id}`; `LeaveHousehold(householdId)`; `GetState(householdId, weekStart)` returns `{ version, list }` where `list` has exactly the shape of `GET .../shopping-lists/{weekStart}` (an empty shape when the week has no list) and `version` is a fingerprint of that content (equal versions = equal lists; it is not ordered). A non-member, or an unknown household, gets `HubException("forbidden")` (indistinguishable, so households cannot be probed). Membership is resolved by `HouseholdMembershipGuard` (same `ITenantResolution.FindRole` as the household middleware, then the `HouseholdMember` policy; no role compared in feature code, rule 2), which also puts the hub method's DbContext into that household's tenant filter.
- Event: server to client **`ShoppingListChanged`** `{ householdId, weekStart, kind, itemId }`, `kind` one of `Generated | ManualItemAdded | ItemChecked | ItemUnchecked | ItemRemoved`, `itemId` null for `Generated`. It is a **refetch signal, not a patch**: no list content travels in the event (so a revoked member left in a group learns nothing but "something changed"), and concurrent edits cannot arrive out of order. It is sent after the change is saved, to the whole household group including the sender's own other tabs. A failing broadcast is logged and never undoes the change.
- Client contract: (1) connect with automatic reconnect; (2) on connect AND on every reconnect (groups do not survive a reconnect) call `JoinHousehold(h)` then `GetState(h, week)` and replace local state with `list`, remembering `version`; (3) on `ShoppingListChanged` for the week on screen (ignore other weeks) call `GetState` again (debounce bursts) and replace local state; skip the re-render if `version` is unchanged; (4) events missed while offline are not replayed, which is why step 2 always refetches; (5) a `forbidden` from Join/GetState means the user left the household: stop and go to household selection. REST remains the write path (checks, adds, generate); the REST GET also works as a fallback when the socket is down.
- Revoked membership: Join and GetState re-check on every call, so a removed member cannot join or read afterwards. Since T-044 (Q-015) removal also evicts live connections: see "Household management" below. What stays: a member removed outside the API (raw SQL) keeps a joined connection, and its content-free `ShoppingListChanged` signals, until it disconnects; and the cookie itself is validated at connect only.
- Antiforgery and origin: the hub is mapped on the app, not on `MapApiRoot` (the root group's antiforgery filter is an endpoint filter and does not apply to hub endpoints; SignalR also maps negotiate without an HTTP method, so the "all unsafe endpoints validate antiforgery" test does not list it). Negotiate is a POST that only hands out a connection id and changes no state; a token the SignalR client cannot send would only break connecting. Cross-site WebSocket hijacking: the auth cookie is `SameSite=Lax`, which browsers withhold from cross-site handshakes and POSTs; `HubOriginMiddleware` additionally rejects (`403`) a request to the hub path whose `Origin` host differs from the request host (covers sibling subdomains, which are same-site). Requests without Origin (non-browser) pass but still need the cookie. The refusal is ProblemDetails `403` with type `urn:foodplanner:problem:forbidden-origin`; `Origin: null` is refused too. Local-only gap: the port is not compared, so another `localhost` port (another dev app on the same machine) passes the check; accepted because it only concerns dev data and the cookie is still required. Vite caveat: with `API_PROXY_TARGET=http://api:8080` and `changeOrigin: true` the proxy rewrites Host to `api` while the browser's Origin stays `localhost`, so the hub answers `403 forbidden-origin`; the default target `http://localhost:5000` is fine. Test `EndpointPolicyTests.Every_hub_endpoint_requires_an_authenticated_user...` pins that no hub endpoint is anonymous.
- Offline copy versioning (T-088): the saved list in localStorage carries a `schema` number (`CACHE_SCHEMA`, `web/app/shopping/storage.ts`). A saved list with another schema or an unexpected shape is deleted and never rendered; bump the number whenever the list response gains a field the page reads. The check-off queue is unversioned and survives updates. The service worker drops its `fp-runtime-api` cache when a new build activates.
- Scale-out limit: with the in-process hub, a second API replica would not see the first's broadcasts. Until Azure SignalR (or a backplane) is added, run the API as one replica.

## Household management (T-044, no migration)
Routes are household-scoped (`/api/households/{h}/...`), so the household middleware has resolved the caller's membership and every query runs through that household's tenant filter. Failures are ProblemDetails.
- `DELETE /api/households/{h}` (**HouseholdOwner**) deletes the household and everything it owns. Delete path: `Households` is the tenant root (no filter, no `HouseholdId`), so the endpoint loads the household whose id the policy just proved the caller owns (`ICurrentHousehold.HouseholdId`, never a body value), removes it, and ONE `DELETE FROM Households` does the rest through the database cascades (Household to Membership, Invite, Recipe, MealPlan, ShoppingList, PantryItem, own Ingredient and Tag, and from those to their children; the NO ACTION foreign keys between tenant tables are checked at the end of the statement, so they do not block it). No `ExecuteDelete`, no filter bypass, no new `ITenantResolution` method. Proof: `HouseholdManagementTests.Deleting_a_household_removes_every_row_of_every_tenant_entity...` seeds one row of EVERY `ITenantEntity`/`ICatalogEntity` in the EF model for two households from the isolation registry (it fails, naming the type, if one has no factory), deletes A through the API and asserts A has zero rows of every type and B is untouched. `AspNetUsers` are global identities and survive. After the commit, and best effort (a storage failure is logged as a warning and does not fail the request; the files are then invisible orphans), the blobs under `{householdId:N}/` in `recipe-images` are deleted. Not undoable: there is no soft delete (it would need a migration; raise a question if wanted). The web client must ask for explicit confirmation (T-045).
- `POST /api/households/{h}/leave` (**HouseholdMember**, Child included) removes the caller's own membership, `204`. The last Owner is refused: `409 last-owner` ("transfer ownership or delete the household"; role changes and ownership transfer are in "Member and invite management" below). Concurrent leaves are serialised by a row lock on the household (a tracked no-op update inside the transaction), so two Owners leaving at once give one `204` and one `409`.
- `DELETE /api/households/{h}/members/{userId}` (**HouseholdOwner**) removes another member, `204`. Refused: yourself (`409 cannot-remove-self`, use leave), another Owner (`409 owner-cannot-be-removed`, demote it first (T-048)), a user who is not a member of THIS household (`404 member-not-found`, also for a member of another household: the lookup goes through the tenant filter).
- Effects of leaving or being removed (T-011 review N6): the membership row is deleted; the person's account, their other households and their history stay (meal plan picks, who checked an item and pantry confirmations keep pointing at the user, so their address stays visible as "picked by"). Invites they created that are still open are expired (`Invite.Revoke`: the row is kept, `ExpiresAt` moves to now, so the link answers `410 invite-invalid`); invites already accepted stay valid and so do the memberships they created. The Restrict foreign keys from `Invites` to `AspNetUsers` therefore block nothing here. Account deletion does not exist; when it does it must not remove a household's last Owner (`Memberships.UserId` cascades, which would orphan the household).
- `GET /api/households/{h}/export` (**HouseholdAdult**: Owner and Adult; a Child gets 403 because the document names members) returns `application/json` with `Content-Disposition: attachment; filename="foodplanner-household-{id:N}.json"` and `Cache-Control: private, no-store`. Format `foodplanner-household-export` version 1: `{ format, version, exportedAt, household: {id, name}, entities: { "<EntityTypeName>": [ { <camelCase property>: value, ..., createdAt, updatedAt } ] }, images: [ {recipeId, version, thumbUrl, cardUrl, fullUrl} ] }`. `entities` is built from the EF model: EVERY `ITenantEntity` and `ICatalogEntity` type, so a new entity is exported with no code change (test: the keys equal the model's household-owned types, each with the exact row ids found in SQL). For catalog entities only the household's OWN rows are exported, never the global seed rows (ingredient, unit and tag ids in the data refer to the global catalog by their stable ids). Left out: `byte[]` properties (the invite token hash, row versions). Membership rows carry the member's `email`. Images are references (relative API URLs a member can fetch), not bytes; base64 was judged not cheap (three sizes per recipe, up to megabytes). The read is not one snapshot: tables are read one after another.
- Live connections (Q-015). `ILiveConnections` (`Api/Realtime`, in-process `LiveConnectionRegistry`, singleton) tracks every hub connection with its user and the households it joined (`JoinHousehold`/`LeaveHousehold`; removed on disconnect). After the database change COMMITS: leave and remove call `EvictUserFromHouseholdAsync` (the user's connections that joined that household leave the group and are aborted; their other connections stay), delete calls `CloseHouseholdAsync` (every connection that joined it), and a security stamp rotation calls `CloseUserAsync` (all of the user's connections). The last is wired into `register` (a resend rotates the stamp) and `confirm-email` today; **any code that rotates a stamp (password change, "log out everywhere") must call it**. `JoinHousehold` registers the join, adds to the group and then re-checks membership, so a removal that commits in between is still caught. A closed client reconnects (if it has automatic reconnect) and its next `JoinHousehold` gets `forbidden`, which per the client contract means "go to household selection". Eviction never throws (failures are logged; the connection then lives until it disconnects, the old behaviour). Limit: the registry only knows this replica's connections, the same single-replica limit as the hub (see Scale-out limit above).

## Member and invite management (T-048, no migration)
All **HouseholdOwner**, household-scoped, failures are ProblemDetails. Queries run through the household's tenant filter, so another household's members and invites are never listed and their ids answer `404` (or `403` when addressed through a household the caller does not own).
- `GET .../members` returns `[{ userId, email, role, joinedAt }]` (oldest first; `joinedAt` is the membership's creation time; the address comes from the global identity table).
- `PUT .../members/{userId}/role` with `{ "role": "Owner" | "Adult" | "Child" }` (name matched like the invite role: case-insensitive, no numbers) returns the updated member. Promotion to Owner is allowed (ownership sharing and transfer: promote, then the old Owner demotes themselves or leaves). The last Owner cannot be demoted: `409 last-owner`. Setting the role a member already has is a `200` no-op. An Owner may demote themselves when another Owner exists. Unknown role `400` (validation problem on `role`), user not in this household `404 member-not-found`.
- `DELETE .../members/{userId}` is the T-044 endpoint, unchanged in behaviour: an Owner is still refused (`409 owner-cannot-be-removed`); demote first. Removal evicts live connections (Q-015, T-044).
- `GET .../invites` lists OPEN invites only (not accepted, not expired, which includes revoked): `[{ id, role, expiresAt, createdAt, createdByUserId }]`. Never the token or its hash; the plain token exists only in the response that created the invite.
- `DELETE .../invites/{inviteId}` revokes an open invite, `204`: it loads the open invite (tenant-filtered) and calls `Invite.Revoke` (`ExpiresAt` moves to now, the row is kept). A redemption that commits between the read and the save keeps its membership; only the already-accepted invite's expiry moves (harmless). The link then answers `410 invite-invalid`. An invite that is not open (accepted, expired, already revoked, unknown, other household) is `404 invite-not-found`.
- Concurrency: leave, remove and role change all take the same household row lock (a tracked no-op update of the `Households` row in the transaction) before reading roles, so "is another Owner left" cannot race. Two Owners demoting each other at once give exactly one `200`; the loser gets `403 forbidden`, because the `HouseholdOwner` policy runs BEFORE the lock, so role change and remove-member re-check under the lock that the caller is still an Owner of the household and change nothing if not (the same `403` as a policy refusal). `409 last-owner` remains for a demotion that would leave no Owner and whose caller is still an Owner (for example demoting oneself as the only Owner). The re-check also stops an Owner demoted a moment ago from completing one in-flight change or removal. Tests: `An_owner_demoted_while_their_role_change_or_removal_waits_for_the_lock_changes_nothing` (holds the lock in SQL, deterministic) and `Two_owners_demoting_each_other_at_once_never_leave_the_household_without_an_owner`.
- Effect of a role change: the household middleware resolves the role from the database on every request (`FindRole`, no cache), so the policies see the new role on the member's next request. There is no realtime push: a demoted member is still a member, keeps their live connection and group, and the content-free `ShoppingListChanged` signals are not role-dependent. A client learns its new role from the next `GET /api/households` (it includes the role); the web client should refetch it when a request answers `403`.
- Logout (T-044 review): `POST /api/auth/logout` also calls `ILiveConnections.CloseUserAsync` for the signed-in user. Connections do not record which cookie opened them, so ALL of the user's connections close, other devices' included; those reconnect and, with a valid cookie, rejoin.
- Export limit (T-044 review): `GET .../export` carries rate-limit policy `household-export`, per user (default 3 per 60 s, `RateLimiting:Export`), `429` with `Retry-After`.

## Recipe import (T-042, migration `AddRecipeImports`; the review UI is T-043, `/recipes/import`, see web/README.md)
Paste text or give a URL, get a draft with structured, matched ingredients, fix what did not match, save as a normal recipe. Rule-based, no LLM (decided by the architect in Q-017; no per-import cost, deterministic, testable); a smarter parser can replace `IngredientLineParser`/`IngredientMatcher` later behind the same draft.
- Artifact (rule 5). `RecipeImport` (`Domain/Imports`, `ITenantEntity`, own Guid key, table `RecipeImports`): `Source` (Url or Text), `SourceUrl`, `RawContent` (the pasted text, or the JSON of the page's Recipe JSON-LD node; cut to 200 000 characters), `DraftJson`, `Status` (Draft, Saved, Discarded), `CreatedByUserId` (FK to the user, NO ACTION), `SavedRecipeId`, `RowVersion`, and the usual `CreatedAt`. The ORIGINAL ingredient text (`Original` per line) exists only in this row; a saved recipe holds ingredient id, quantity, unit id and a short note. The draft is JSON on the row, so it has no child tables and no foreign keys to ingredients or units: every id in it is re-resolved through the filtered sets (global plus own) whenever it is written to a recipe, so the Q-012/T-073 rules hold (another household's id is `400`, same as an unknown one). `SavedRecipeId` is a plain column, not a foreign key (a deleted recipe leaves it dangling, harmlessly; a foreign key would add a second cascade path). Only cascade: Household -> RecipeImport. Registered in the isolation harness. Discarding (`DELETE`) sets `Discarded` and erases `RawContent` and `DraftJson`; saving does the same in the transaction that creates the recipe (Q-017): `RawContent` and `DraftJson` become null, while `SourceUrl` (provenance) and `SavedRecipeId` stay, so the original text lives only while the import is a Draft. A GET of a Saved import therefore shows an empty draft with its status and recipe id. A household can hold at most 50 drafts (`409 import-limit`), which bounds storage.
- Line parser (`IngredientLineParser`, pure). "2 dl melk", "1/2 ts salt", "1½ cup flour", "3 egg", "200 g smør, myk", "2-3 fedd hvitløk", "ca. 200 g ost", "en klype salt", "a pinch of salt", "500ml vann", "1 boks (400 g) tomater" become quantity, unit, ingredient text and note. Numbers: integers, decimal point or comma, fractions, mixed numbers, unicode fractions (½ ⅓ ¾ ... and the fraction slash), ranges (`2-3`, `2 til 3`, `1 to 2`); a range keeps the UPPER bound as the quantity (enough to buy) and writes the range in the note. Units come from `UnitWords` (aliases of the seeded codes: dl, ss/tbsp/spiseskje, ts/tsp/teskje, kopp/cup, g/gram, kg, ml, l, stk, fedd/clove, klype/pinch, ...); a quantity with no unit word is `stk` ("3 egg", flagged `UnitImplied`); a unit word the catalog lacks (boks, pk, pose, oz, lb, ...) is kept as `UnitText` and the line is "unmatched unit". No quantity means "to taste" (`salt`, `smør til steking`; the phrase goes to the note). Parentheses and text after the first (non-decimal) comma become the note (capped at 200 characters). `salt og pepper` / `salt & pepper` with no amounts splits into two lines (short parts only). Section labels ("Til sausen:") are headings and dropped; a line with no letters, zero or absurd amounts or no ingredient is `Unparseable` and kept as an unparsed line with only its original text.
- Pasted text (`PastedRecipeParser`): with headings (Ingredienser/Ingredients, Fremgangsmåte/Method/Instructions, ...) the text between them is used; without, the first line is the title, then amount-led or short lines are ingredients and everything from the first sentence (or numbered line) on is steps. Servings ("Porsjoner: 4", "Til 4 personer", "Serves 6", "Gir 12 stykker") and times ("Forberedelse: 10 min", "Koketid: 1 time 15 min", "Cook time: 20 minutes") are read from short lines. Step text is cleaned (`StepTextCleaner`): tags and entities removed, numbering and bullets stripped, whitespace collapsed, control characters dropped, 2000 characters at most.
- Page JSON-LD (`RecipeJsonLdExtractor`, pure; the fetch is Infrastructure): all `application/ld+json` blocks of the page (or the response itself when it is JSON-LD), tolerating comment markers, CDATA, trailing commas and raw line breaks in strings; the Recipe node is found as a single object, an array, `@graph`, nested (`mainEntity`), `@type` as string or array. Fields: `name`, `description`, `recipeIngredient` (list or one string), `recipeInstructions` (text, list, `HowToStep`, `HowToSection` with `itemListElement`, HTML), `recipeYield` (number, text, list: the first number, 1-100 else none), `prepTime`/`cookTime`/`totalTime` (ISO 8601; with only a total, the total is stored as cook time), `image` (URL, list or `ImageObject`; absolute http(s) only). The image URL is a candidate in the draft; nothing is downloaded. No Recipe found: `422 import-no-recipe-found` ("paste the text instead").
- Matcher (`IngredientMatcher`, pure). Candidates are the household's visible ingredients (global plus own, through the tenant filter, so never another household's), each with every name: English, Norwegian (translations) or the one typed name. Best score wins: exact normalized name 1.0; same after light nb/en plural stemming and folding of æøå 0.95 ("gulrøtter" = Gulrot); same with spaces or word order ignored 0.93 ("rød løk" = Rødløk); the words of the shorter of text and name all inside the longer 0.7 to 0.9 ("rød paprika" finds Paprika, "yoghurt" finds "Yoghurt naturell"); a close spelling (edit distance at most 2, names of 5+ letters, scaled by length, at most 0.95). The text is also tried without descriptors (fersk, hakkede, finely, chopped, ...) at x0.95. Threshold 0.8 (`IngredientMatcher.Threshold`); below it, or when two different ingredients tie below 0.95 ("oil": Olive oil, Rapeseed oil), the line stays unmatched and up to three suggestions (score >= 0.5) are returned. At an equal score the household's own ingredient wins over a global one. Line status: `Matched` (ingredient known; quantity and unit both known, or both null), `UnmatchedIngredient`, `UnmatchedUnit` (a quantity without a catalog unit), `Unparsed`.
- Endpoints under `/api/households/{h}/imports`, all **HouseholdAdult** (Owner and Adult; Child and non-members get 403): `GET` (drafts waiting, newest first, so an abandoned one can be discarded), `POST` `{ url }` or `{ text }` (exactly one; text up to 100 000 characters; `201` with the draft: title, description, servings (4 assumed and warned when absent), times, `imageUrl`, steps, lines (`position`, `original`, `ingredientText`, `quantity`, `quantityLow`, `unitText`, `unitId/Code/Name`, `ingredientId/Name`, `confidence`, `note`, `status`, `suggestions`), `warnings`, `canSave`), `GET /{id}`, `PUT /{id}` (a field left out stays as it is; `lines` are edits by `position`: ingredient (required), then quantity+unit and note, which stay as parsed when left out (so resolving an ingredient never drops the parsed amount); `toTaste: true` clears quantity and unit (not combinable with them); an empty `note` clears it; or `remove`; to use a new ingredient, create it first with `POST /ingredients`), `POST /{id}/save` (`201` with `{ recipeId }` and a Location), `DELETE /{id}` (`204`). Another household's import id is `404 import-not-found` (so is a discarded one); an import that is Saved or Discarded cannot be edited, saved or discarded again (`409 import-not-draft`); a concurrent change is `409 import-conflict`.
- Save. Every line must be `Matched`, else `400` ValidationProblem on `lines[i].ingredientId` (unmatched or unparsed) or `lines[i].unitId` (unmatched unit), naming the original text. Then the recipe is created by the same code as `POST /recipes` (`RecipeEndpoints.TryCreateAsync`: the same validation and the same filtered-set resolution; its errors come back as `lines[i]...`, `title`, `servings`), and the import is marked Saved in the same transaction. The row version makes two saves at once one recipe (the other gets `409`).
- SSRF-safe fetch (`Infrastructure/Import`, `SafeWebPageFetcher`; the only outbound HTTP from a user-supplied URL, enforced by the architecture test `OutboundHttpRulesTests`). (1) Only absolute `http`/`https` URLs of at most 2000 characters, no user info, ports 80 and 443 only; an IP literal is judged at once. (2) The connection is made by our own `SocketsHttpHandler.ConnectCallback`: it resolves the name through `IHostResolver`, refuses the WHOLE answer if any address is not public (`IpAddressRules`: 0/8, 10/8, 100.64/10 CGNAT, 127/8, 169.254/16 incl. the 169.254.169.254 metadata address, 172.16/12, 192.0.0/24, 192.0.2/24, 192.88.99/24, 192.168/16, 198.18/15, 198.51.100/24, 203.0.113/24, multicast and reserved 224/3; IPv6: everything outside 2000::/3, plus Teredo/IETF 2001::/23, documentation ranges; IPv4-mapped, NAT64 and 6to4 addresses are judged by the IPv4 address they carry) and connects to a vetted address, so the checked address is the connected address (no DNS rebinding window) and every new connection, redirect hops included, is vetted again. (3) Redirects are followed by hand, at most 3, each target through (1) and (2). (4) No proxy, no cookies, no credentials, a fixed `User-Agent` (`FoodplannerRecipeImport/1.0`). (5) Only `text/html` and `application/ld+json`; the body is streamed (after decompression, so a gzip bomb counts at its inflated size) and refused beyond 2 MB; one 10 second timeout covers connecting, redirects and reading. Limits are `RecipeImport:MaxBytes`, `TimeoutSeconds`, `MaxRedirects`; no setting widens the address or port rules (tests replace the `IFetchPolicy` registration with one that allows loopback and any port to reach a local test server, never production configuration).
- Fetch failures are ProblemDetails: `400 import-url-not-allowed` (invalid, blocked or non-public address; one answer for all so it does not reveal what exists), `422 import-unsupported-content`, `422 import-too-large`, `422 import-no-recipe-found`, `502 import-fetch-failed` (error status, host not found, reset), `504 import-fetch-timeout`. Details never include the upstream body. URL imports are rate limited per user, 10 per 10 minutes (`RateLimiting:UrlImport`, checked by `UrlImportRateLimiter` once the body is bound, so text imports are not counted): `429 rate-limited` with `Retry-After`.
- Hardening details. At most 4 fetches run at once per process (`RecipeImport:MaxConcurrentFetches`; a semaphore, not a queue): when saturated the answer is `503 import-busy`. Like the in-process SignalR hub (ADR 0007), the cap, the rate limiter and the per-user counters are per replica, so with several replicas the real limits multiply until a shared store replaces them. A corrupt gzip/deflate/brotli body is a fetch failure (`502 import-fetch-failed`), never a 500. Only the charsets utf-8, iso-8859-1, windows-1252 and utf-16 are honoured; any other (utf-7 included) is read as UTF-8. `OutboundHttpRulesTests` also requires `PublicInternetPolicy` to be the only `IFetchPolicy` in `src`.
- `RecipeImports.CreatedByUserId` is a NO ACTION foreign key to the user. Any future account deletion must first delete or reassign that user's imports (like meal plan picks and pantry confirmations), or it will fail.
- Not done / known limits: images are not downloaded (the candidate URL is shown only); no scheduled cleanup of old Saved or Draft imports (the 50 draft cap bounds the draft rows); the parser knows only the seeded units and Norwegian/English phrasing (an unknown unit word is flagged, never guessed); a recipe that needs an ingredient the household lacks needs `POST /ingredients` first (T-043 can offer it inline).

FROM RecipeImports WHERE SavedRecipeId = Recipes.Id` (same household, only http/https URLs) sets `SourceUrl`. `SourceName` is left NULL on purpose and derived from the host when the API reads the recipe (`Recipe.SourceDisplayName`), so the host parsing exists in one place; a later edit stores the name. ## Managing own ingredients (T-079, no migration)
A household cleans up its own ingredients (for example clumsy ones left by a recipe import). Global catalog rows stay read-only. Routes under `/api/households/{h}/ingredients`, all **HouseholdAdult** (Owner and Adult; Child and non-members get `403 forbidden`); failures are ProblemDetails.
- `GET .../ingredients/own?search=` lists only the household's own ingredients (name in the request language is the typed name), sorted like the catalog list, each with `usage { recipes, pantryItems, shoppingLists, importDrafts }`: distinct recipes, pantry rows (0 or 1), distinct shopping lists (weeks) holding a generated item, and open import drafts whose lines use it (read from the draft JSON, at most 50 drafts). Counts go through the tenant-filtered sets, so another household's references never count.
- `PUT .../ingredients/{id}` `{ name }` renames (same normalisation and rules as create: unique among own rows and the global catalog in every language, case-insensitive; `409 ingredient-exists`; the row itself is excluded, so changing only the case is fine). References keep the id, so nothing else changes.
- `DELETE .../ingredients/{id}`: `204` when nothing references it, else `409 ingredient-in-use` with the counts as an extension member `usage` and the advice to merge. Open import drafts that only name it as a match suggestion are scrubbed in the same save. A reference that appears between the check and the delete is refused by the NO ACTION foreign key and answered the same `409`.
- `POST .../ingredients/{id}/merge` `{ targetIngredientId }` moves every reference to the target and deletes the source; `200 { target, moved, warnings }`. Warnings are codes: `dimension-differs` (source and target are normally measured in different dimensions, so amounts may stay separate lines on a list) and `staple-differs`. The units of existing quantities are never converted.
- Errors. The source id is resolved through the filtered set: another household's row or an unknown id is `404 ingredient-not-found`; a global row is `403 ingredient-global` (for rename, delete and merge alike). The target id comes from the body, so by the Q-012 rule an unknown or other household's id is `400` ValidationProblem on `targetIngredientId` (the same answer for both); the target may be global or own. `targetIngredientId` equal to the source is `400 ingredient-merge-into-self`. A concurrent change (a recipe edit that added a line for the source, a stale row, another merge) rolls the whole merge back and is `409 ingredient-conflict`.
- Merge design (`IngredientMerger`), ONE transaction, tracked updates only (the `ExecuteUpdate`/`ExecuteDelete` ban holds; the save-time check T-073 sees every changed key): (1) `RecipeIngredient` lines get the target id. (2) Pantry: unique per `(household, ingredient)`. No target row: the source row moves. Target row exists: `PantryItem.Absorb` keeps the more recent confirmation (user and time) and the later expiry (no expiry counts as latest), and the source row is removed. (3) Shopping list items (generated; unique per `(list, ingredient)`): in a list without a target item the source item is re-pointed (keeps its id and checked state); in a list that has one the source item is removed (its quantity and source rows go with it by cascade). (4) Open import drafts: `DraftJson` lines and suggestions are rewritten (`ImportDraft.ReplaceIngredient`); saved and discarded imports hold no draft. (5) Every affected week is then regenerated from the plan with the normal generator and reconciler (`ShoppingListEndpoints.GenerateFromPlanAsync`/`ApplyAsync`): quantities are re-merged exactly with `QuantityMerger` (Mass with Mass, Volume with Volume, other dimensions stay separate lines), sections follow the target's staple flag, a checked item whose amount changed gets `quantityChangedSinceChecked`. A stale list is thus also brought up to date; this is the one side effect to know about. (6) The source is removed. After the commit each regenerated week sends the usual `Generated` hub signal (T-034).
- Model coverage. `IngredientReferences.Handled` lists the foreign keys to `Ingredient` that merge and the in-use check handle (`RecipeIngredient`, `ShoppingListItem`, `PantryItem`); the test `Every_foreign_key_to_ingredient_in_the_model_is_handled_by_merge` derives the foreign keys from the EF model and fails, naming them, if one is added without being handled. T-076 (alternative ingredients) must add its references to the merger, the usage counts and that list. No new entity, so nothing new for the isolation harness.
- Web: `/ingredients` ("Your ingredients", linked from household settings for Owner and Adult; a Child sees a note and no calls are made): filter, usage line, inline rename, delete with confirmation (the `409` shows the counts and suggests merging), merge via the catalog search (global and own, excluding the source) and a confirmation naming the counts.

## Ingredient amount kind, purpose, optional and alternatives (T-076, Q-018, migration `AddIngredientKindPurposeAlternatives`)
"Salt etter smak" is not an amount but is on the prep list; "margarin til steking" is a cooking fat that can be butter or oil, and how it is used belongs in the steps. The ingredient list is the prep list: what to have ready, grouped by what it is for.
- Model (`Domain/Recipes`). `RecipeIngredient` gains `AmountKind` (`Measured` | `ToTaste` | `AsNeeded`), `Purpose` (`Main` | `Frying` | `Serving` | `Garnish` | `Seasoning`) and `IsOptional`. `AmountRules` (pure) is the one rule: Measured needs a quantity and a unit; ToTaste and AsNeeded forbid both (the constructor throws, the endpoint answers `400` on `ingredients[i].quantity`/`unitId`/`amountKind`/`purpose`). "To taste" is therefore an explicit kind, no longer a missing quantity. A request that leaves `amountKind` out is inferred (a quantity means Measured, none means ToTaste), so older clients keep working. Stored as text (`nvarchar(20)`) like `Tag.Kind`; defaults Measured, Main, false.
- Alternatives. `RecipeIngredientAlternative` is an `ITenantEntity` with its own Guid id (the T-012 model rules reject owned entities), `RecipeIngredientId` (cascade from its line only, so no second cascade path from the recipe), `Position` and `IngredientId` (NO ACTION; global or own ingredient). Up to 5 per line (`400` on `ingredients[i].alternativeIds`), never free text. Every id is resolved through the filtered `Ingredients` set before saving (another household's id and an unknown id are both `400` on `ingredients[i].alternativeIds[j]`), and the save-time reference check (T-073) covers the foreign key without any code, because it is derived from the EF model. An alternative must differ from the line's own ingredient; repeated ids are ignored. Registered in the isolation harness. The recipe response lines carry `amountKind`, `purpose`, `isOptional` and `alternatives` (`ingredientId`, `ingredientName` in the request language); PUT replaces lines and alternatives together (a second save in the same transaction, because the alternatives need the generated line ids).
- Migration: the three columns are added with the defaults, then `UPDATE RecipeIngredients SET AmountKind = 'ToTaste' WHERE Quantity IS NULL` (Purpose stays Main). `MigrationTests.AddIngredientKindPurposeAlternatives_...` shows it.
- Scaling (`RecipeScaling.Scale(kind, ...)`): only a Measured quantity is scaled; ToTaste and AsNeeded are returned unchanged for any number of servings (`GET .../scaled` returns them as they are).
- Shopping list generation (`ShoppingListGenerator`, `PlannedIngredient` gets kind, purpose, optional). A line is bought by amount only when `NeedsBuying`: Measured, not optional, and not "a few spoonfuls of frying fat" (Purpose Frying, a volume of at most 45 ml = 3 ss after scaling; frying fat in grams is still bought). An ingredient with no such line in any planned recipe goes to CheckYouHave with no quantity (ToTaste, AsNeeded, optional, small frying fat); if another recipe does need it, it stays on the main list and its quantity is the sum of the bought lines only (the checked lines add recipes to "from", not to the amount). Staples still always go to CheckYouHave. Reconciliation is unchanged: an item that changes section moves and starts unchecked. The pantry (T-037) works as before: confirmed staples are removed from CheckYouHave on generate; a non-staple can still not be confirmed.
- Alternatives on the list. The list stores no alternatives. `GET` shopping list items carry `alternatives` (id, name), read from the contributing recipes' lines (`ShoppingAlternatives.For`: the union in first-seen order, without the item itself); the web shows "eller margarin, olje" / "or ...".
- Import (`IngredientLineParser`, pure; nb and en). Phrases that the structured fields fully represent are removed from the text, so the note holds only the rest: "etter smak"/"to taste" -> ToTaste + Seasoning; "til steking/stekning/steiking", "å steke i", "for frying" -> Purpose Frying (AsNeeded when there is no amount, Measured when there is: "2 ss smør til steking"); "til servering"/"to serve" -> Serving; "til pynt/dekorasjon"/"to garnish" -> Garnish (AsNeeded without an amount); "etter behov"/"as needed" -> AsNeeded; "kan sløyfes/utelates", "valgfritt", "optional", a leading "evt."/"eventuelt" or a lone "(evt.)" -> IsOptional; "til pensling/smøring" -> AsNeeded but the phrase stays in the note. A line with no amount and no phrase ("salt og pepper", split in two) -> ToTaste + Seasoning. "X eller Y [eller Z]", "X or Y", "X, evt. Y" -> primary X and alternatives (at most 5, no digits, at most 5 words each); a generic last alternative ("annen kokt, hvit fisk") is completed from the text after the comma. The draft builder matches each alternative to the catalog (a generic one also by its last words: "annen hvit ost" finds Ost); a match becomes `alternativeIds`, anything else (no match, or the same ingredient as the primary) stays in the note as text ("eller margarin"), never as a free-text entity. When the primary part does not match, the whole unsplit text is tried, then "adjective + last words" ("rød eller gul paprika" finds Paprika). Draft lines (JSON, no foreign keys) carry `amountKind`, `purpose`, `isOptional`, `alternativeIds`; a draft saved before T-076 is read with ToTaste for lines without a quantity. The line status is `UnmatchedUnit` while a Measured line lacks quantity or unit, or a ToTaste/AsNeeded line has one. `PUT /imports/{id}` line edits take `amountKind`, `purpose`, `isOptional`, `alternativeIds` with patch semantics (absent keeps; `toTaste: true` equals `amountKind: ToTaste`; a non-measured kind clears quantity and unit and must not be combined with them); `ingredientId` is still required. - Managing own ingredients (T-079 extended). `RecipeIngredientAlternatives.IngredientId` is in `IngredientReferences.Handled`. ## Catalog: margarine and oils (T-084, migration `AddMargarineAndOils`)
Three global ingredients were added to `IngredientSeed` (seed ids are UUIDv5 from the key, never changed): `margarin` Margarin / Margarine (Mass, staple, like Smør), `olje` Olje / Oil (Volume, staple, like Rapsolje) and `noytral_olje` Nøytral olje / Neutral oil (Volume, staple). The seed now has 110 ingredients. The migration only inserts rows and translations (idempotent: EF records it as applied; the fixed ids make a replay conflict instead of duplicate). Decisions:
- **Dimension and staple.** Margarine is Mass because recipes give it in g and the shop sells it by weight; exactly like Smør (there is no density, so a "2 ss" line stays a separate Volume line, the normal `QuantityMerger` rule). Oils are Volume. All three are staples (never auto-added to a shopping list), consistent with Smør, Rapsolje and Olivenolje.
- **Clash with a household's own ingredient of the same name** (for example "Nøytral olje" or "Margarin eller olje" from an earlier import). The database cannot clash: the unique index is on `(HouseholdId, Name)` and the global row's `Name` is the English name. Global wins from now on: creating or renaming an own ingredient to any of the new names in either language is `409 ingredient-exists`. Existing own rows are left untouched and keep working (recipes, lists, pantry, drafts keep their ids). In the importer an exact own match and an exact global match tie and the household's own row wins (T-042), so existing behaviour does not change until the household merges its row into the global one on the Ingredients screen (T-079 merge; `dimension-differs` is a warning, not an error). Nothing is merged automatically; the seed never touches household rows.
- **Matching.** "margarin", "olje", "oil", "nøytral olje", "neutral oil" are exact matches (1.0); the same words as T-076 alternatives ("smør eller margarin", "olje til steking") now become catalog alternatives instead of a note. "Oil" alone is therefore no longer ambiguous between Rapsolje and Olivenolje.

## Translatable catalog data (T-039, Q-013, migration `AddCatalogTranslations`)
- Locales: `nb` and `en` (`Domain/Localization/Locales`). Code, keys and the final fallback are English. Global catalog rows (ingredients, units, tags) are named in every locale; text a household types (its own ingredients, tags, recipe titles, manual list items) is stored once and returned as typed in every locale.
- Storage: table `CatalogTranslations` (`CatalogTranslation`, key `(Kind, EntityId, Locale)`, `Name` up to 100; kind is `ingredient`, `unit` or `tag`, the same strings as the seed id kinds). A locale is data, so adding one needs no schema change: add it to `Locales.Supported`, to the seed data files and to `Locales.FromLanguageTag`, and a migration for the new rows. The row's own `Name` column holds the English name (it is also the last fallback and keeps the existing unique index). Global only: on `TenantCoverage.Exempt`, no `HouseholdId`, written only by the seed (`HasData`, composite key, ids unchanged), never at request time. Seed data stays in one file per type (`IngredientSeed`, `UnitSeed`, `TagSeed`: `Name` = English, `Nb` = bokmål; 110 ingredients, 11 units, 13 tags). A unit's `Code` is the stable identity and is not translated; responses add `unitName`.
- Language negotiation: `Accept-Language` is parsed with q-values (`Locales.Negotiate`): nb/no/nn (any region) gives `nb`, en gives `en`, q=0 is ignored, nothing supported or no header gives `en`. Endpoints take a `RequestLocale` parameter (minimal-API `BindAsync`, so it is not in the OpenAPI parameters). The SignalR hub reads the header of the connection request. The web client sends `Accept-Language` from the app's active locale (`web/app/api/client.ts`).
- Name resolution: the requested translation, else the English translation, else the row's `Name` (`CatalogNames.WithNames`, a SQL left join, so search, sort and paging happen in the database on the localized name). Sorting uses a SQL Server collation per locale (`Norwegian_100_CI_AS` for nb, so æ ø å sort after z; `Latin1_General_100_CI_AS` for en) instead of an in-memory culture comparer, because Take/paging must be decided in SQL and the runtime image may have no ICU; the id is the tie-breaker so paging is stable. Search is a case-insensitive "contains" on the localized name (the requested language only). Shopping list items are sorted in memory (the list is small) with a nb-NO or en-US culture comparer.
- Duplicate checks (`POST` ingredients and tags) compare a household name against the visible rows' own names and against the translations of every locale of the global rows, case-insensitively: "Løk" and "onion" are both `409`.
- Generated shopping list items store `IngredientId` and unit ids only, never a name, so the list is re-labelled when the language changes. Recipe detail returns `ingredientName`, `unitCode` (stable) and `unitName` in the request language; recipe and list tags are localized and ordered by kind, then localized name.

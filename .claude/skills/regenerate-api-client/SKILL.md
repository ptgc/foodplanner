# Regenerate the API client

The contract is OpenAPI and the TS types are generated (CLAUDE.md rule 6, ADR 0001). Two files are generated and committed:

| File | Generated from | By |
|---|---|---|
| `openapi/openapi.v1.json` | the Api's endpoint metadata (`src/Api/OpenApi/OpenApiSetup.cs`) | `scripts/openapi.sh` / `scripts/openapi.ps1` |
| `web/app/api/schema.d.ts` | `openapi/openapi.v1.json` | `web/scripts/api-types.mjs` (openapi-typescript, pinned in `web/package.json`) |

`web/app/api/client.ts` is the hand-written wrapper (`api`, openapi-fetch, antiforgery and language middleware). It holds no API types.

## When to run it

1. After you add, remove or change a route, method, route or query parameter, request or response record, enum, or a
   `Produces...` status (the add-endpoint skill, step 14).
2. When `./scripts/verify.sh` fails at
   - step `test` with `OpenApiDocumentTests.Generated_document_is_valid_and_matches_committed_file`: the document is stale;
   - step `web-api-check` with "api:check FAILED: app/api/schema.d.ts is out of date": the TS types are stale.
3. Not needed after pulling `dev`: both files are committed with the backend change that caused them.

A frontend task that needs an endpoint or field that is not in `openapi/openapi.v1.json` yet does not add it to the types.
The backend change comes first (its own task, or a question to the architect).

## The exact commands

Run from the repo root, in this order (the second reads the output of the first):

```bash
./scripts/openapi.sh
npm --prefix web run api:generate
```

```powershell
.\scripts\openapi.ps1
npm --prefix web run api:generate
```

4. `scripts/openapi.sh` runs
   `OPENAPI_UPDATE=1 dotnet test --project tests/Api.Tests --filter-class Foodplanner.Api.Tests.OpenApiDocumentTests`:
   the test builds the Api in memory and writes the document instead of comparing it. Api.Tests start their SQL Server
   Testcontainer as an assembly fixture, so keep the container engine running.
5. `npm --prefix web run api:generate` runs `node scripts/api-types.mjs generate` and rewrites `app/api/schema.d.ts`.
   On a fresh clone run `npm --prefix web ci` first (the script uses `web/node_modules/openapi-typescript`).
6. Check: `npm --prefix web run api:check` and `npm --prefix web run typecheck`. Typecheck shows every screen that a
   changed contract breaks; fix those call sites, not the types.

## Commit

7. Commit `openapi/openapi.v1.json` and `web/app/api/schema.d.ts` together with the endpoint change that caused them,
   on the same task branch.
8. Read the diff of both files. A change you did not make (another route, a renamed schema) means the endpoint metadata
   changed in a way you did not intend: fix the endpoint, do not keep the surprise.

## Never hand-edit the generated files

9. Never edit `web/app/api/schema.d.ts` (its header says "auto-generated by openapi-typescript"; ESLint ignores it) or
   `openapi/openapi.v1.json`. The next generate overwrites the edit, and the checks fail until then.
10. Never write an API type by hand in `web/app`. Use the generated ones:
    ```ts
    import { api } from "../api/client";
    import type { components } from "../api/schema";
    type Entry = components["schemas"]["PantryItemResponse"];
    api.GET("/api/households/{householdId}/pantry", { params: { path: { householdId }, query: { includeExpired: true } } });
    ```
    (from `web/app/routes/pantry.tsx`). Test fixtures use the same types (`web/app/routes/pantry.test.tsx`).
11. If a generated type is wrong (a field should be nullable, a status is missing, a parameter has no `uuid` format), fix the
    endpoint's metadata or record in `src/Api` and regenerate.

## Review checklist

- Both generated files changed together with the endpoint change, and nothing else changed in them.
- No hand edits in `schema.d.ts` or `openapi.v1.json`; no hand-written request or response types in `web/app`.
- `api:check` and the OpenAPI document test pass in `verify.sh`.
